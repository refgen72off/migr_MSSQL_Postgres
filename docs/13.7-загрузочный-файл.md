# 13.7 Загрузочный файл pgloader

Инструкция к этапу 7 плана (вторая половина). Результат этапа: загрузочный файл (или набор
файлов) лежит в репозитории, не содержит секретов, `--dry-run` проходит, состав объектов и
порядок загрузки соответствуют решениям 13.4–13.5.

## 1. Режимы загрузки

| Режим | Когда | Что в файле |
|---|---|---|
| **A. pgloader создаёт схему** (наш основной) | схема простая, переименований мало | `create tables`, `create indexes`, `no foreign keys`; индексы pgloader строит **после** копирования данных |
| **B. Схема готовится вручную** | много ручных решений по типам, именам и ограничениям | `create no tables`, `create no indexes`; таблицы создаются из DDL, pgloader только грузит данные |

Режим B даёт полный контроль и обязателен, если правила `CAST` не покрывают все колонки или
таблицы создаются с партиционированием/табличными пространствами.

Важно про умолчания: для MSSQL по умолчанию включены `include drop`, `create tables`,
`create indexes`, `reset sequences`, `foreign keys`, `downcase identifiers`. `include drop`
удаляет одноимённые таблицы в приёмнике (с `CASCADE`) — на общем стенде это недопустимо, поэтому
он снимается явно.

## 2. Полный пример с пояснениями

```
LOAD DATABASE
     FROM mssql://{{MSSQL_USER}}:{{MSSQL_PWD}}@{{MSSQL_HOST}}:1433/{{MSSQL_DB}}
     INTO postgresql://{{PG_USER}}@{{PG_HOST}}:5432/{{PG_DB}}

 WITH include no drop,            -- не удалять объекты в приёмнике
      create tables,               -- таблицы создаёт pgloader
      create indexes,              -- индексы строятся после копирования данных
      no foreign keys,              -- ФК создаём отдельно, после проверки данных
      create schemas,              -- схемы источника переносятся как есть
      reset no sequences,          -- identity донастраиваем вручную (13.9)
      downcase identifiers,        -- имена к нижнему регистру (решение 13.4)
      truncate,                    -- на повторном прогоне чистить целевые таблицы
      workers = 8,
      concurrency = 4,
      prefetch rows = 50000,
      batch rows = 10000,
      batch size = 20 MB,
      max parallel create index = 2,
      on error stop

 SET work_mem to '64MB',
     maintenance_work_mem to '2GB',
     statement_timeout to '0',
     search_path to 'public'

 CAST type nvarchar  to varchar keep typemod,    -- nvarchar(max) без typemod -> varchar без длины (эквивалент text)
      type nchar     to char    keep typemod,
      type varchar   to varchar keep typemod,
      type char      to char    keep typemod,
      type numeric   to numeric keep typemod,
      type decimal   to numeric keep typemod,
      type money     to numeric drop typemod,   -- если нужна точная (19,4) — ALTER TABLE после загрузки (13.9): грамматика CAST typemod не принимает
      type smallmoney to numeric drop typemod,
      type datetime  to timestamp drop typemod,
      type datetime2 to timestamp drop typemod,
      type smalldatetime to timestamp drop typemod,
      type datetimeoffset to timestamptz drop typemod,   -- правил по умолчанию нет (как и для date/time/text/ntext/image — см. 13.4)
      type date     to date,
      type time     to time

 ALTER SCHEMA 'dbo' RENAME TO 'app'

 BEFORE LOAD DO
   $$ create schema if not exists app; $$,
   $$ alter table if exists app.orders set (autovacuum_enabled = false); $$;

 AFTER LOAD DO
   $$ comment on table app.orders is 'loaded by pgloader'; $$;
```

Пояснения к каждой группе клауз:

**WITH** — поведение загрузки. `on error stop` останавливает прогон на первой ошибке PostgreSQL
(нужно на пилоте и на приёмочном прогоне); `on error resume next` продолжает, складывая «плохие»
строки в `reject.dat`/`reject.log` (нужно на исследовательских прогонах). `truncate` безопасен
только вместе с `include no drop`: он чистит данные, но не сносит объекты.

**SET** — сессионные параметры PostgreSQL. `statement_timeout to '0'` обязателен: иначе
серверный таймаут убьёт долгую загрузку большой таблицы.

**CAST** — правила из 13.4. Пользовательские правила проверяются раньше встроенных, выигрывает
первое совпавшее.

**ALTER SCHEMA** — переименование схемы на лету. Фильтры `INCLUDING/EXCLUDING` и
`ALTER TABLE NAMES MATCHING` работают с **исходными** именами, поэтому переименование схемы на них
не влияет.

**BEFORE/AFTER LOAD DO** — единственное место, где можно выполнить произвольный SQL вокруг
загрузки. Здесь же включается/выключается autovacuum и создаются объекты, которых pgloader не
делает.

## 3. Отдельные файлы для больших таблиц

Крупные таблицы выносятся в свои файлы: падение одной не сбрасывает весь прогон, а параметры
подбираются индивидуально.

```
LOAD DATABASE
     FROM mssql://{{MSSQL_USER}}:{{MSSQL_PWD}}@{{MSSQL_HOST}}:1433/{{MSSQL_DB}}
     INTO postgresql://{{PG_USER}}@{{PG_HOST}}:5432/{{PG_DB}}

 WITH include no drop, create tables, create indexes, no foreign keys,
      create schemas, reset no sequences, downcase identifiers, truncate,
      workers = 4, concurrency = 2, prefetch rows = 20000, batch rows = 5000,
      on error stop

 SET work_mem to '128MB', maintenance_work_mem to '2GB', statement_timeout to '0'

 INCLUDING ONLY TABLE NAMES LIKE 'Documents%' IN SCHEMA 'dbo'
 ALTER SCHEMA 'dbo' RENAME TO 'app';
```

Фильтр для MSSQL использует синтаксис `LIKE` (`%`, `_`), регулярные выражения не поддерживаются —
это отличие от MySQL-источника. Несколько паттернов задаются списком через запятую в одной клаузе
(`LIKE 'a%', 'b%' IN SCHEMA 'dbo'`) или повторением полной клаузы; `IN SCHEMA` для MSSQL-фильтра
обязательна (в грамматике MSSQL нет формы фильтра без схемы, в отличие от SQLite).

Порядок запуска: сначала справочники и мелкие таблицы (быстро видно ошибки типов), затем крупные,
затем таблицы с LOB. Порядок фиксируется в протоколе.

## 4. Повторный прогон и «догон» отдельных таблиц

pgloader не умеет «догрузить изменения»: повторный запуск перезаливает таблицу целиком. Отсюда
два приёма:

1. **Перезагрузка одной таблицы** — отдельный файл с `INCLUDING ONLY TABLE NAMES LIKE
   'Orders' IN SCHEMA 'dbo'` и `truncate`.
2. **Догон по времени** — фильтрация на источнике через представление:

```
 MATERIALIZE VIEWS orders_delta AS $$
   select * from dbo.Orders where UpdatedAt >= '2026-11-18T22:00:00'
 $$
```

`MATERIALIZE VIEWS` создаёт представление на источнике, грузит его как таблицу и удаляет после
загрузки. Это единственный штатный способ отфильтровать данные: произвольного `WHERE` в
загрузочном файле нет.

## 5. Проверка файла до запуска

```bash
pgloader --dry-run ms.load                  # парсит файл и проверяет соединения с обоими концами
```

`--dry-run` для MSSQL **не печатает DDL и не грузит данные**: он проверяет синтаксис load-файла и
обе строки подключения. Это быстрая проверка до прогона, но итоговых типов и списка таблиц она
не покажет. Как реально увидеть DDL до боевого прогона:

1. **контрольный прогон `with "schema only"` в отдельную БД-песочницу** — pgloader создаст
   таблицы и индексы без данных; DDL сверяется с решениями 13.4 прямо по приёмнику;
2. **SQL-лог настоящего прогона** — `--debug` (или лог с уровнем SQL) печатает генерируемые
   `CREATE TABLE`/`CREATE INDEX`; смотреть в файле лога с ограниченными правами, не в консоли.

Что проверять по песочнице/логу:

- таблицы создаются с ожидаемыми типами (`varchar(n)`, `numeric`, `timestamp`) — сверка с 13.4;
- имена в нижнем регистре, схема — целевая;
- в списке нет таблиц, которые должны остаться вне миграции;
- нет `DROP` (если `include drop` не снят — увидите его здесь и остановитесь).

Полезные флаги на время отладки:

| Флаг | Зачем |
|---|---|
| `--dry-run` | проверить load-файл и соединения, без загрузки данных |
| `--on-error-stop` | остановиться на первой ошибке (перекрывает `WITH on error resume next`) |
| `--verbose` | подробный лог: таблицы, батчи, ошибки |
| `--logfile <файл>` | лог в файл с ограниченными правами |
| `--summary <файл>.csv` | машиночитаемая сводка: таблицы, строки, время, ошибки |
| `--root-dir <каталог>` | где хранить батчи, `reject.dat` и временные файлы |
| `--with "prefetch rows = 20000"` | разово переопределить опцию без правки файла |

`--summary` с расширением `.csv`/`.json` — самый удобный вход для протокола прогона (13.8) и для
сверки количества строк (13.10).

## 6. Хранение и версионирование

- В репозитории лежат только файлы с `{{переменными}}` — без паролей, имён серверов заказчика и
  строк подключения. Имена хостов тоже выносятся в переменные: репозиторий публичный.
- Для каждого окружения — свой набор переменных или INI-контекст (13.6), а не своя копия файла.
- Изменения правил `CAST` и фильтров — отдельным коммитом с указанием причины: это следствие
  решений 13.4, а не «подкрутили на ходу».
- Рядом с файлом — короткий `README` в каталоге загрузки: порядок запуска, что делается вручную
  (ФК, identity, CHECK), какие таблицы вынесены отдельно.

## Готово, когда

- [ ] загрузочный файл (файлы) лежит в репозитории и не содержит секретов;
- [ ] умолчание `include drop` снято осознанно, либо объяснено, почему оно нужно;
- [ ] `no foreign keys` и `reset no sequences` соответствуют решениям 13.4/13.9;
- [ ] правила `CAST` перенесены из `cast-rules.txt` без потерь;
- [ ] схема переименована, поиск в логах не показывает `dbo` в целевых объектах;
- [ ] фильтры включают ровно те таблицы, которые нужны, и проверены по списку инвентаря;
- [ ] крупные таблицы вынесены, порядок запуска зафиксирован;
- [ ] `--dry-run` проходит, в нём нет `DROP` и неожиданных типов;
- [ ] `statement_timeout` не мешает, `work_mem` задан сессионно, а не глобально;
- [ ] параметры `workers`/`concurrency`/`prefetch` подобраны по пилоту, а не «на глаз».

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| пропали таблицы на стенде | `include drop` по умолчанию | `include no drop`, объекты создавать самому |
| все текстовые колонки стали `text` | встроенные правила MSSQL отбрасывают длину | `keep typemod` в `CAST` (13.4) |
| правило `CAST` «не работает» | его перекрыло более раннее правило | порядок правил: частное выше общего |
| загрузка упала на середине большой таблицы | таймаут сервера | `SET statement_timeout to '0'`, `--on-error-stop` только на пилоте |
| в приёмнике есть лишние таблицы | фильтр `INCLUDING` написан regex-синтаксисом | для MSSQL — `LIKE`: `'Orders%'`, а не `~/^Orders/` |
| «догон» не отфильтровал строки | нет `WHERE`-клаузы в DSL | `MATERIALIZE VIEWS` в staging-схему + слияние (13.11, раздел 7); фильтровать живую таблицу приёмника нельзя |
| ФК создались и загрузка встала на порядке строк | `foreign keys` включены по умолчанию | `no foreign keys`, ФК — в 13.9 |
| в логах пароль | `--verbose` печатает строку подключения целиком | убрать `--verbose` из боевого прогона, права на лог |
| `ESRAP-PARSE-ERROR` на последней клаузе, хотя синтаксис кажется верным | команда не закончена `;` (правило `end-of-command`; примеры официальных доков pgloader `;` не показывают) | завершать команду точкой с запятой |
