# 13.3 Снимок исходной базы

Инструкция к этапу 3 плана. Снимок — это эталон, с которым потом сравнивается результат
миграции. Без него проверка превращается в «посмотрели глазами»: любые расхождения в данных
обнаруживаются уже в проде.

Что фиксируется: количество строк по каждой таблице, агрегаты по ключевым колонкам, DDL, список
индексов, FK, дефолтов, identity-колонок, collation, версии MSSQL и целевой СУБД.

## 1. Когда снимать

| Момент | Зачем |
|---|---|
| Этап 3 (сразу после проверки копии) | базовый эталон, на нём строится пилот и оценка объёма |
| T-0, непосредственно перед полной загрузкой | на живой базе данные меняются: снимок этапа 3 к моменту загрузки уже неверен |
| После загрузки в Tantor (этап 10) | сравнение с T-0, а не с этапом 3 |

Правило: **свежесть снимка должна совпадать со свежестью эталона**. Если между снимком и
загрузкой база принимала записи, сравнивать с эталоном бессмысленно — нужен пересъём в окне.

Снимок этапа 3 снимается на том же состоянии, что и проверенная копия: либо сразу после её
восстановления на стенде (лучше — тогда эталон неподвижен), либо на источнике в момент
минимальной нагрузки. Предпочтителен вариант «на восстановленной копии»: данные в ней
зафиксированы и не меняются под руками.

## 2. Структура каталога

Всё — **вне репозитория** (имена объектов и данные заказчика в публичный репозиторий не
попадают). Корень `<каталог-миграции>` выбираете вы (правило из 13.1): локальный каталог,
сетевая папка или защищённое хранилище команды.

```
<каталог-миграции>\<БД>\snapshot\
  T0-2026-11-18\
    meta.md                     паспорт снимка
    30-rowcounts.csv            точные счётчики строк
    31-aggregates.csv           агрегаты по колонкам
    32-metadata/                индексы, FK, дефолты, identity, collation (из 13.1)
    33-hashes/                  хеши упорядоченных выгрузок
    34-schema/                  DDL (dacpac + sql из 13.2)
```

Шаблоны и генераторы лежат в репозитории (`docs/`, `tools/`), выгрузки — нет.

## 3. Паспорт снимка (`meta.md`)

Обязательные поля: дата и время (локальное и UTC), сервер, БД, версия и patch level источника,
collation базы, compatibility level, `last_lsn` проверенной копии (из 13.2), версия целевой
СУБД (планируемая или фактическая), кто снимал, на каком состоянии снято (источник / копия).

```sql
SELECT @@SERVERNAME                          AS server_name,
       DB_NAME()                             AS db_name,
       @@VERSION                             AS version_string,
       SERVERPROPERTY('ProductVersion')       AS product_version,
       SERVERPROPERTY('ProductLevel')        AS patch_level,
       DATABASEPROPERTYEX(DB_NAME(),'Collation') AS db_collation,
       (SELECT compatibility_level FROM sys.databases WHERE database_id = DB_ID()) AS compat_level,
       (SELECT sqlserver_start_time FROM sys.dm_os_sys_info) AS instance_start_time,
       SYSUTCDATETIME()                      AS snapshot_utc,
       SYSDATETIMEOFFSET()                   AS snapshot_local_with_offset,  -- локальное время СО смещением
       SYSDATETIME()                         AS snapshot_local;
```

## 4. Точные счётчики строк

Точный счёт — `COUNT_BIG(*)`, а не `sys.partitions`: последний не работает для memory-optimized
таблиц и не годится как эталон. Запрос генерируется по каталогу, чтобы не писать его руками:

```sql
-- 30-rowcounts.sql   (контекст: БД; результат — одна таблица: schema, table, rows)
SET NOCOUNT ON;

CREATE TABLE #counts (schema_name sysname, table_name sysname, row_count bigint);
DECLARE @sch sysname, @tab sysname, @sql nvarchar(max), @obj nvarchar(600);

DECLARE cur CURSOR LOCAL FAST_FORWARD FOR
    SELECT s.name, t.name
    FROM sys.tables t JOIN sys.schemas s ON s.schema_id = t.schema_id
    WHERE t.is_ms_shipped = 0
    ORDER BY s.name, t.name;

OPEN cur; FETCH NEXT FROM cur INTO @sch, @tab;
WHILE @@FETCH_STATUS = 0
BEGIN
    SET @obj = QUOTENAME(@sch) + N'.' + QUOTENAME(@tab);
    SET @sql = N'INSERT INTO #counts SELECT @s, @t, COUNT_BIG(*) FROM ' + @obj + N';';
    EXEC sp_executesql @sql, N'@s sysname, @t sysname', @s = @sch, @t = @tab;
    FETCH NEXT FROM cur INTO @sch, @tab;
END
CLOSE cur; DEALLOCATE cur;

SELECT schema_name, table_name, row_count FROM #counts ORDER BY schema_name, table_name;
```

Стоимость: `COUNT_BIG(*)` по большой таблице читает индекс (обычно самый узкий) — это не
бесплатно. Для баз от сотен гигабайт счётчик снимается в окно минимальной нагрузки или по
частям (по схемам), с фиксацией времени начала и конца в `meta.md`.

## 5. Агрегаты по колонкам

Счётчика строк мало: одинаковое количество строк может скрывать подмену значений, потерю
кириллицы, обрезание строк, сдвиг дат. Поэтому по каждой таблице снимаются агрегаты в «длинном»
формате — одна строка на метрику. Такой файл удобно сравнивать построчно (`diff`), в отличие от
широкой таблицы.

Формат и набор метрик для таблицы `s.t`:

```sql
SELECT N's.t' AS object_name, N'cnt'        AS metric, CAST(COUNT_BIG(*) AS nvarchar(64)) AS value FROM [s].[t]
UNION ALL
SELECT N's.t', N'nulls.status',  CAST(COUNT_BIG(*) - COUNT([status]) AS nvarchar(64)) FROM [s].[t]
UNION ALL
SELECT N's.t', N'count.status',  CAST(COUNT([status]) AS nvarchar(64)) FROM [s].[t]
UNION ALL
SELECT N's.t', N'sum.amount',    CAST(SUM(CAST([amount] AS decimal(38,6))) AS nvarchar(64)) FROM [s].[t]
UNION ALL
SELECT N's.t', N'min.amount',    CAST(MIN([amount]) AS nvarchar(64)) FROM [s].[t]
UNION ALL
SELECT N's.t', N'max.amount',    CAST(MAX([amount]) AS nvarchar(64)) FROM [s].[t]
UNION ALL
SELECT N's.t', N'min.created_at', CAST(DATEDIFF_BIG(SECOND, CAST('19700101' AS datetime2), MIN([created_at])) AS nvarchar(20)) FROM [s].[t]
UNION ALL
SELECT N's.t', N'max.created_at', CAST(DATEDIFF_BIG(SECOND, CAST('19700101' AS datetime2), MAX([created_at])) AS nvarchar(20)) FROM [s].[t];
```

Правила выбора метрик:

| Тип колонки | Метрики |
|---|---|
| числовые, `money`, `numeric`, `decimal` | `sum` (через `decimal(38,6)`), `min`, `max`; `numeric`/`decimal` шире 32 разрядов — без `sum` (переполнит `decimal(38,6)`, сверьте хешами) |
| `date`, `datetime`, `datetime2`, `smalldatetime` | `min`, `max` — **epoch-секундами**, не строками |
| `datetimeoffset` | `min`, `max` epoch-секундами (конвертируется к `datetime2`, смещение теряется — проверяется отдельно, см. 13.1, раздел 8) |
| `time` | `min`, `max` как строки — только для чтения человеком, не для diff |
| любые строковые, `uniqueidentifier`, `binary` | `count`, `nulls` (содержимое проверяется хешами, раздел 7) |
| `float`/`real` | только `count`, `nulls`: суммы и сравнения плавающих значений между СУБД нестабильны |

Пустые агрегаты (`NULL` — пустая таблица) выводятся генератором как строка `NULL`, чтобы поле
в CSV не оказалось пустым.

Уточнение по датам: строковое представление `min`/`max` между MSSQL и PostgreSQL не совпадает
(разное число знаков дробной части), поэтому для **машинного** сравнения даты снимаются как целые
секунды эпохи (`DATEDIFF_BIG(SECOND, CAST('19700101' AS datetime2), col)`), а не как строки —
правило и примеры в 13.10, раздел 4.2.

Скрипт-генератор: `tools/generate-aggregates.ps1` — читает каталог колонок и печатает такой
запрос для всех таблиц сразу. Запуск:

```powershell
powershell -ExecutionPolicy Bypass -File tools\generate-aggregates.ps1 `
  -Server <сервер> -Database <БД> -OutFile <каталог-миграции>\<БД>\snapshot\T0-2026-11-18\31-aggregates.sql

sqlcmd -S <сервер> -d <БД> -E -i <каталог-миграции>\<БД>\snapshot\T0-2026-11-18\31-aggregates.sql `
  -o <каталог-миграции>\<БД>\snapshot\T0-2026-11-18\31-aggregates.csv -W -s ";" -w 8000
```

Сгенерированный SQL просматривается перед запуском: скрипт пишет шаблон, а не гарантию
корректности. Для баз с сотнями таблиц генератор вызывается по схемам (`-Schema dbo`), иначе
запрос получается слишком большим для одного батча.

## 6. DDL, индексы, FK, дефолты, identity, collation

Новых запросов здесь нет — переиспользуются выгрузки 13.1 и 13.2, но с **обязательной
перепроверкой на T-0**:

| Артефакт | Источник | Обновляется на T-0 |
|---|---|---|
| DDL схемы (dacpac + .sql) | 13.2, раздел 5 | да |
| индексы | 13.1, `06-indexes.csv` | да |
| PK/UK/FK/CHECK/DEFAULT | 13.1, `07-constraints.csv` | да |
| identity и последовательности (текущие значения) | 13.1, `08-identity-sequences.csv` | да — значения меняются |
| типы и collation колонок | 13.1, `10-types-detail.csv`, `11-collation-mismatch.csv` | да |
| права, роли, логины | 13.1, `16`–`18` | да |
| версии MSSQL | 13.1, `01-passport.csv` | нет |
| версия целевой СУБД | `SELECT version()` на Tantor | записывается, когда стенд готов |

Сравнение «этап 3 → T-0» делается построчным `diff` CSV. Любое расхождение — либо
согласованное изменение (фиксируется в `meta.md`), либо повод пересобрать загрузочный файл.

## 7. Полная сверка содержимого: упорядоченная выгрузка + SHA-256

Агрегаты ловят грубые расхождения. Точное доказательство «данные совпали» даёт только
побайтовое сравнение одинаково нормализованных выгрузок. Метод:

1. По каждой таблице выгружаются все строки в детерминированном порядке (`ORDER BY` по
   первичному ключу; если ключа нет — по всем колонкам).
2. Столбцы приводятся к тексту по единым правилам нормализации (ниже).
3. Файл хешируется SHA-256. Хеш попадает в `snapshot\...\33-hashes\<schema>.<table>.sha256`,
   сам файл выгрузки можно не хранить.
4. На стороне PostgreSQL выгрузка строится по тем же правилам и хешируется тем же способом.

Правила нормализации (нарушение любого пункта делает сравнение бессмысленным):

| Тип | Как приводить |
|---|---|
| `date` | `YYYY-MM-DD` |
| `datetime`, `datetime2` | `YYYY-MM-DDTHH:MM:SS.ffffff` без часового пояса |
| `datetimeoffset` | `YYYY-MM-DDTHH:MM:SS.ffffff±HH:MM`, смещение сохраняется |
| числовые, `money` | фиксированное число знаков (для `money` — 4), точка как разделитель, без разделителей разрядов |
| `float`/`real` | `17` значащих цифр (`R`/`G17`) — либо исключить колонку из сверки и сверить агрегатами |
| `bit` | `0`/`1` |
| `uniqueidentifier` | нижний регистр, с дефисами (`D`-формат) |
| `binary`/`varbinary` | hex в нижнем регистре |
| строки | как есть, без `TRIM`, но с явным правилом для `NULL` (например, `\N`) |
| разделитель полей | символ, не встречающийся в данных (обычно `\t`), экранирование запрещено |
| кодировка файла | UTF-8 без BOM, перевод строки `\n` |
| окончание строки | ровно один `\n`, в том числе у последней строки |

Выгрузка средствами `sqlcmd` с такими правилами не гарантируется (он форматирует значения
сам), поэтому для критичных таблиц используется `bcp` с явным форматом или промежуточный
`SELECT ... FOR XML/JSON` с последующей нормализацией скриптом. Цена вопроса — несколько
«эталонных» таблиц (деньги, документы, справочники), а не вся база: полная побайтовая сверка
всех таблиц редко укладывается в окно.

Практическое правило отбора: полностью сверяются 5–10 таблиц, где ошибка дороже всего
(финансовые регистры, договоры, остатки); остальные проверяются агрегатами из раздела 5.

## 8. Как понять, что база менялась между снимком и загрузкой

| Признак | Как проверить |
|---|---|
| аптайм экземпляра меньше ожидаемого | `sqlserver_start_time` в `meta.md` |
| были записи после снимка | `sys.dm_db_index_usage_stats.last_user_update` по таблицам |
| есть колонка-метка изменения | `rowversion`, `updated_at`, `modify_date` — взять `MAX` и сравнить |
| схема изменилась | `sys.objects.modify_date` новее даты снимка |
| счётчики строк разошлись | сравнить `30-rowcounts.csv` T-0 с текущими значениями |

Если записи были — снимок T-0 переснимается в окне; сравнивать «T-0 до записей» с результатом
загрузки нельзя.

## 9. Формат сравнения

Файл `31-aggregates.csv` сравнивается с таким же файлом, снятым на Tantor, обычным `diff`
(или `Compare-Object` в PowerShell). Правила:

- сравнение построчное по ключу `object_name;metric`, значение — строка, поэтому форматирование
  должно совпадать: числа без разделителей, даты в ISO;
- допустимое расхождение — **ноль**; любое отличие объясняется отдельной строкой в протоколе
  (например, «округление `numeric(19,4)` → `numeric` выровнено явным `CAST`»);
- расхождения группируются: «тип», «пустые значения», «кодировка», «даты», «денежные суммы»;
  это же деление используется в отчёте этапа 10.

## Готово, когда

- [ ] `meta.md` заполнен: время (UTC и локальное), версии, collation, `last_lsn`, состояние базы;
- [ ] `30-rowcounts.csv` снят точным `COUNT_BIG(*)`, а не по метаданным;
- [ ] `31-aggregates.csv` снят по правилам раздела 5, `float` исключён из сумм;
- [ ] DDL, индексы, FK, дефолты, identity, collation, права обновлены на T-0 и сравнены с этапом 3;
- [ ] выбраны 5–10 таблиц для полной побайтовой сверки, правила нормализации зафиксированы;
- [ ] хеши этих таблиц посчитаны и сохранены;
- [ ] снимок T-0 сделан в окне, после чего записи в источник прекращены (или дельта учтена);
- [ ] ни один файл снимка не попал в публичный репозиторий.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| счётчики строк совпали, а данные разошлись | сравнивались только количества | агрегаты и хеши, раздел 5 и 7 |
| агрегаты «не сходятся» на `float` | плавающая точка и разный формат вывода | исключить `float` из сумм, сверять `count`/`nulls` |
| суммы разошлись на копейки | `money` → `numeric`, разная точность и округление | явный `CAST` и фиксированный масштаб в обеих СУБД |
| даты разошлись на 3 часа | `datetime` → `timestamptz` и часовой пояс сервера | фиксировать TZ в `meta.md`, проверять `datetimeoffset` отдельно |
| кириллица «поехала» | выгрузка в cp1251 и чтение как UTF-8 (или наоборот) | нормализация: UTF-8 без BOM на обоих концах |
| хеши не совпали, хотя данные верны | разный порядок строк или формат чисел | детерминированный `ORDER BY`, единые правила раздела 7 |
| снимок T-0 снят, но загрузка была позже на час | база продолжала принимать записи | снимок в окне после останова записи либо дельта |
