# 13.12 Переключение приложения и откат

Инструкция к этапам 10–11 плана. Результат: приложение работает на Tantor, простой закрыт в
согласованное окно, источник остаётся доступным для сверки и отката, точка невозврата объявлена
явно и зафиксирована.

## 1. Ворота перед переключением

Переключение не начинается, пока не выполнено всё:

| Ворота | Проверка |
|---|---|
| Код перенесён | процедуры/функции/триггеры/представления/задания созданы (13.9) и вызываются приложением |
| Валидация подписана | протокол 13.10 с pass по всем пунктам |
| Дельта применена (если нужна) | 13.11, финальный LSN применён и сверен |
| Бэкап приёмника | полная копия + проверенное восстановление средствами PostgreSQL (настройка — 13.5) |
| Мониторинг видит приёмник | дашборды и алерты включены **до** переключения |
| Сборка приложения готова | версия с новым драйвером и строкой подключения собрана и протестирована на стенде |
| Откат отрепетирован | шаги раздела 6 пройдены на стенде, известны время и владелец решения |

## 2. Что меняется в приложении

Переключение — это не «правка строки подключения». Полный список:

**2.1. Строка подключения и драйвер.**

| MSSQL | PostgreSQL |
|---|---|
| `Server=host;Database=db;User Id=...;Password=...` | `Host=host;Port=5432;Database=db;Username=...;Password=...` |
| `Microsoft.Data.SqlClient` / `System.Data.SqlClient` | `Npgsql` (ADO.NET), JDBC PostgreSQL, `psycopg` |
| `Encrypt=True;TrustServerCertificate=False` | `SSL Mode=Require;Trust Server Certificate=false` |
| `Command Timeout=30` | `Command Timeout=30` (Npgsql), `Options='-c statement_timeout=30s'` |
| `Application Name=...` | `Application Name=...` |
| `MultipleActiveResultSets=True` | не требуется (MARS — особенность MSSQL) |
| `Pooling=True;Max Pool Size=100` | `Pooling=true;Maximum Pool Size=100` |
| — | `Search Path=app,public` (если схема не `public`) |

**2.2. Типы на стороне клиента.** Самая частая причина падений после «успешного» переноса:

- `timestamp` (без зоны) Npgsql отдаёт как `DateTime` с `Kind=Unspecified`, `timestamptz` — с
  `Kind=Utc`. Если код ставит `DateTime.Now` в `timestamptz` — ошибка или сдвиг. Решение
  фиксируется один раз: либо колонки `timestamp` + `DateTime.Now`, либо `timestamptz` +
  `DateTime.UtcNow`;
- `bit` → `boolean`: 0/1 превращается в `false/true`, старые проверки `= 1` в коде надо править;
- `money` → `numeric`: тип в приложении остаётся `decimal`, но масштаб теперь явный;
- `uniqueidentifier` → `uuid`: часть ORM ожидает `Guid`, часть — строку;
- `varchar(n)` vs `text`: ORM-маппинги с `HasMaxLength` могут ругаться на несоответствие.

**2.3. SQL-диалект.** Полная таблица замен — 13.13; в переключении проверяется, что в коде не
осталось: `TOP`, `ISNULL`, `+` для строк, `GETDATE()`, `LEN`, `CHARINDEX`, `DATEPART`, `IIF`,
`ISNUMERIC`, `MERGE`, `OUTPUT`, `SCOPE_IDENTITY`, `@@IDENTITY`, `sp_executesql`, `WITH (NOLOCK)`,
`#temp`, `SELECT ... INTO`, `EXEC('...')`.

**2.4. Транзакции и изоляция.**

- `READ COMMITTED` в MSSQL блокирует читателей на время записи; в PostgreSQL читатели не
  блокируются (MVCC). Логика, полагавшаяся на блокировки, ведёт себя иначе;
- `READ_COMMITTED_SNAPSHOT` ближе всего к `READ COMMITTED` PostgreSQL, но не идентичен;
- вложенные транзакции MSSQL (`BEGIN TRAN` внутри `BEGIN TRAN`) — в PostgreSQL это `SAVEPOINT`,
  а `ROLLBACK` внутренней транзакции откатывает только точку сохранения;
- `XACT_ABORT ON` аналога не имеет: обработка ошибок переносится в код.

**2.5. Обработка ошибок.** Коды MSSQL заменяются на `SQLSTATE`:

| Событие | MSSQL | PostgreSQL |
|---|---|---|
| нарушение уникальности | 2627, 2601 | `23505` |
| нарушение FK | 547 | `23503` |
| NOT NULL | 515 | `23502` |
| дедлок | 1205 | `40P01` |
| таймаут блокировки | 1222 | `55P03` |
| сериализация | 3960 | `40001` |

Ретраи пишутся по `SQLSTATE`, а не по тексту сообщения.

**2.6. Пакетные операции.** `SqlBulkCopy` → `COPY` (`NpgsqlBinaryImporter`, `COPY ... FROM STDIN`);
массовые `INSERT ... VALUES (...), (...)` работают, но по-другому планируются.

**2.7. Регистр имён.** Если выбрано `downcase identifiers`, все запросы с `"MixedCase"` в кавычках
падают. Проверка: поиск по коду `"` вокруг имён таблиц и колонок.

## 3. Последовательность окна

```
T-7д   снизить TTL DNS до 60 с (если переключение через DNS)
T-1д   финальная сборка приложения, smoke-тесты на стенде, инструкция на бумаге
T-60   проверки: приёмник жив, бэкап есть, мониторинг работает, дельта догоняет
T-30   остановка записи в приложении (или перевод источника в READ ONLY)
T-30   финальный LSN, применение дельты (13.11), последовательности, ANALYZE
T-15   быстрая сверка: счётчики по изменённым таблицам, 3–5 эталонных запросов
T-10   переключение строк подключения / DNS / alias, rolling restart приложений
T-5    smoke-тесты бизнес-функций (создать заказ, провести документ, построить отчёт)
T+0    объявление об успехе либо решение об откате (владелец, письменно)
T+30   первый контрольный срез метрик: ошибки, длительность запросов, блокировки
T+24ч  ежедневный обзор в течение наблюдения (этап 9 плана)
```

Команды для фиксации состояния источника на момент останова:

```sql
-- MSSQL: запрет записи без остановки экземпляра (после отключения приложений)
ALTER DATABASE [source_db] SET READ_ONLY WITH ROLLBACK IMMEDIATE;
-- внимание: ROLLBACK IMMEDIATE откатывает активные транзакции без сохранения;
-- перед выполнением убедиться (sp_who2 / sys.dm_exec_sessions), что пользовательских
-- активных сессий нет
-- возврат при откате:
ALTER DATABASE [source_db] SET READ_WRITE;
```

```sql
-- PostgreSQL: убедиться, что приложение действительно переключилось
SELECT application_name, client_addr, count(*)
FROM pg_stat_activity WHERE datname = 'target_db' GROUP BY 1,2;
```

## 4. Smoke-тесты (минимум)

1. Чтение справочника, поиск по кириллице в верхнем и нижнем регистре.
2. Создание записи с автоинкрементом → проверить, что `id` выдался и следующий не конфликтует.
3. Проведение документа с триггером → проверить запись в аудите (ровно одна).
4. Отчёт за период → сумма совпадает с эталоном 13.10.
5. Операция, которая раньше ловила дедлок → выполняется, ошибок нет.
6. Две параллельные транзакции по одной строке → поведение осознанное (блокировка/ошибка).

## 5. Точка невозврата

Объявляется письменно и до окна, а не в момент паники.

| До точки | После точки |
|---|---|
| откат = вернуть строку подключения и снять READ ONLY с источника | откат = потерять данные, записанные в приёмник после переключения, либо делать обратную миграцию |
| окно: до первого успешного smoke-теста бизнес-функции | окно: после него |

Обратная миграция (PostgreSQL → MSSQL для записей, сделанных после переключения) в плане **не
предусмотрена**: это отдельный проект. Поэтому окно «переключились, но пишем куда-то ещё» должно
быть коротким, а источник — оставаться только для чтения.

## 6. Откат

**6.1. Откат до точки невозврата (штатный сценарий):**

1. Остановить приложения (rolling restart не обязателен, достаточно остановки записи).
2. Вернуть строку подключения / DNS / alias на MSSQL.
3. `ALTER DATABASE [source_db] SET READ_WRITE;`
4. Запустить приложения, проверить smoke-тесты на источнике.
5. Зафиксировать в протоколе время, причину и что сделано с приёмником (оставлен для разбора или
   очищен).

**6.2. Откат после точки невозврата:**

1. Приложения останавливаются.
2. Приёмник восстанавливается из копии, снятой до переключения средствами PostgreSQL (бэкап
   настроен на этапе 5, 13.5), — данные, записанные после переключения, теряются.
3. Источник переводится в `READ_WRITE`, приложение возвращается на него.
4. Инцидент разбирается отдельно; решение об обратной миграции принимает владелец системы.

**6.3. Триггеры отката** (фиксируются заранее): ошибки, которые не лечатся за 15 минут;
расхождение данных, подтверждённое сверкой; недоступность приёмника; деградация ключевого отчёта
свыше согласованного допуска.

## 7. После переключения

- Первые 24 часа: ошибки приложения, длительность запросов (`pg_stat_statements`), блокировки,
  рост таблиц/WAL, `temp` файлы, deadlocks.
- Источник остаётся доступным (READ ONLY) минимум до подписания приёмки; затем — по регламенту:
  финальная копия, отзыв доступа, остановка, архивирование.
- Мониторинг и алерты переводятся на новые пороги (они другие: в PostgreSQL нет `Page Life
  Expectancy`, зато есть `bloat`, `temp files`, `xid age`).
- Регламент бэкапа приёмника проверяется на практике: первая копия после переключения + пробное
  восстановление.

## Готово, когда

- [ ] все ворота раздела 1 закрыты;
- [ ] приложение работает с приёмником, `pg_stat_activity` показывает его подключения;
- [ ] smoke-тесты пройдены, аудит не задвоен, автоинкремент работает;
- [ ] ошибки приложения за первый час — в пределах ожидаемого, разобраны;
- [ ] источник переведён в READ ONLY и не принимает записи;
- [ ] точка невозврата объявлена и записана с временем;
- [ ] протокол окна заполнен: таймстемпы, кто что делал, результат smoke-тестов;
- [ ] план наблюдения на первые сутки назначен, ответственный известен.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `28P01` / `password authentication failed` | пароль приложения не создан в PG или `pg_hba` | создать роль, строку в `pg_hba`, проверить до окна |
| приложение падает на конверсии `DateTime` | `timestamp` vs `timestamptz` и `Kind` | привести типы и код к одному решению (2.2) |
| «не найдена таблица» | `search_path` не включает схему | `Search Path=app,public` в строке подключения |
| запросы с `TOP` падают | диалект не перенесён | 13.13, правка кода до окна |
| дедлоки участились | другая модель блокировок | разобрать конкретные запросы, порядок обновления строк |
| после отката приложение видит старые данные | записи ушли в приёмник, источник не обновлялся | это и есть цена перехода точки невозврата |
| простой растянулся | не был готов код/права | ворота раздела 1 |
