# 13.2 Резервная копия MSSQL и проверка восстановления

Инструкция к этапу 2 плана. Результат этапа: полная копия базы, **восстановление которой
проверено**, плюс сохранённые экспорт схемы, список объектов, права и настройки соединений.
Копия без проверки восстановления считается отсутствующей.

## 1. Подготовка

**Права.** Роль `db_backupoperator` в БД (или `db_owner`); для проверки восстановления на
отдельном экземпляре — права на создание БД там. `sysadmin` для бэкапа не требуется. Дополнительно
для этой инструкции: чтение `msdb` (история бэкапов, раздел 2 — `db_datareader` на `msdb` или
снимает DBA) и серверные права `VIEW SERVER STATE` / `VIEW ANY DEFINITION` для DMV раздела 6.

Скрипт создания учётной записи выполняет DBA источника от имени `sysadmin`/`securityadmin`
(как и в 13.1 — разовая административная операция; сам логин дальше используется только для
работ по этой инструкции). Имя логина — пример:

```sql
-- 00-create-backup-login.sql   (контекст: master; выполнять от sysadmin/securityadmin)
USE master;

-- 1. Логин. Если уже существует — шаг пропустить.
--    Не называйте логин db_backupoperator: это имя встроенной роли,
--    совпадение имён делает скрипты и протоколы нечитаемыми.
CREATE LOGIN migr_backup WITH PASSWORD = N'<сложный пароль>',
     CHECK_POLICY = ON,
     DEFAULT_DATABASE = [<БД>];

-- 2. Права уровня экземпляра: DMV раздела 6 (сервис, порты, шифрование, конфигурация).
--    Как и в 13.1, выдаются в контексте master.
GRANT VIEW SERVER STATE   TO migr_backup;
GRANT VIEW ANY DEFINITION TO migr_backup;

-- 3. Роль dbcreator: RESTORE в новую БД, VERIFYONLY / FILELISTONLY, DROP DATABASE
--    (права CREATE DATABASE покрывают и команды проверки копии из раздела 3)
ALTER SERVER ROLE dbcreator ADD MEMBER migr_backup;

-- 4. Права на целевую БД: BACKUP DATABASE (COPY_ONLY, COMPRESSION, CHECKSUM)
USE [<БД>];
CREATE USER migr_backup FOR LOGIN migr_backup;
ALTER ROLE db_backupoperator ADD MEMBER migr_backup;

-- 5. msdb: история бэкапов (msdb.dbo.backupset, раздел 2)
USE msdb;
CREATE USER migr_backup FOR LOGIN migr_backup;
ALTER ROLE db_datareader ADD MEMBER migr_backup;
```

Замечания к скрипту:

- `db_backupoperator` даёт `BACKUP DATABASE`/`BACKUP LOG` и `CHECKPOINT`, но не чтение данных —
  для этой инструкции этого достаточно.
- путь в `TO DISK` — это путь **файловой системы сервера/контейнера SQL Server**, а не клиента:
  учётная запись службы SQL Server должна иметь право записи туда (для контейнера — том,
  примонтированный в него).

**Место.** Свободное место на целевом томе ≥ объёма файлов данных (при `COMPRESSION` обычно
хватает 30–50%; уже сжатые данные не сожмутся, а TDE-базы сжимаются при `MAXTRANSFERSIZE ≥ 128 КБ`
— с SQL 2016; выбранное ниже 4 МБ подходит). Проверка:

```sql
-- выполняется в контексте самой БД: sys.master_files под db_backupoperator может вернуть пусто
USE <БД>;
SELECT DB_NAME(database_id) AS db, type_desc,
       CAST(SUM(size) * 8 / 1024.0 AS decimal(18,1)) AS size_mb
FROM sys.database_files
GROUP BY type_desc;
```

**Влияние на нагрузку.** `COMPRESSION` добавляет CPU, `CHECKSUM` — минимальные накладные
расходы, но обе опции нужны: без контрольной суммы копия может «успешно» записаться битой.
Для большой базы бэкап планируется в окно минимальной нагрузки, длительность фиксируется.

**Имя файла** собирается одинаково во всех прогонах (дата + тип + версия):

```
\\backup-host\mssql\<БД>\<БД>_FULL_COPY_20261118_2200.bak
```

`COPY_ONLY` обязателен, если на источнике работают регламентные задания бэкапа: такая копия не
ломает цепочку дифференциальных копий и не сдвигает базу для их расписания. Плата за это —
`COPY_ONLY`-копия не может служить базой для дифференциального бэкапа; для наших целей
(восстановить и сверить) это не нужно.

## 2. Полная копия

```sql
BACKUP DATABASE [<БД>]
TO DISK = N'\\backup-host\mssql\<БД>\<БД>_FULL_COPY_20261118_2200.bak'
WITH COPY_ONLY,
     COMPRESSION,
     CHECKSUM,
     INIT,
     STATS = 5,
     MAXTRANSFERSIZE = 4194304;
```

Что означает каждая опция:

| Опция | Зачем |
|---|---|
| `COPY_ONLY` | не вмешиваться в регламентную цепочку копий источника |
| `COMPRESSION` | меньше объём и меньше время записи; CPU-плата |
| `CHECKSUM` | контрольная сумма страниц; позволяет обнаружить битую копию при проверке |
| `INIT` | перезаписать файл, а не дописывать в него (проверить, что файл одноразовый: `INIT` затирает существующие backup set'ы в нём) |
| `STATS = 5` | прогресс в выводе, полезно для протокола и оценки длительности |
| `MAXTRANSFERSIZE` | крупные блоки для сетевого тома |

Фиксация факта и метрик копии:

```sql
SELECT TOP (5) database_name, type, backup_finish_date,
       CAST(backup_size / 1048576.0 AS decimal(18,1))            AS size_mb,
       CAST(compressed_backup_size / 1048576.0 AS decimal(18,1)) AS compressed_mb,
       database_backup_lsn, first_lsn, last_lsn,
       DATEDIFF(second, backup_start_date, backup_finish_date)    AS seconds,
       physical_device_name
FROM msdb.dbo.backupset bs
JOIN msdb.dbo.backupmediafamily mf ON mf.media_set_id = bs.media_set_id
WHERE database_name = '<БД>'
ORDER BY backup_finish_date DESC;
```

`last_lsn` — точка, на которую снята копия. Она понадобится, если выбран вариант с дельтой
(раздел 5.3 плана): дельта должна начинаться не раньше этой точки, иначе часть изменений
потеряется или применится дважды.

## 3. Проверка копии без восстановления

```sql
RESTORE VERIFYONLY
FROM DISK = N'\\backup-host\mssql\<БД>\<БД>_FULL_COPY_20261118_2200.bak'
WITH CHECKSUM;
```

Успешный `VERIFYONLY` — необходимое, но **не достаточное** условие: он проверяет читаемость и
контрольные суммы, но не то, что база запустится и данные в ней целы. Поэтому — раздел 4.

Метаданные копии (для протокола):

```sql
RESTORE HEADERONLY
FROM DISK = N'\\backup-host\mssql\<БД>\<БД>_FULL_COPY_20261118_2200.bak';

RESTORE FILELISTONLY
FROM DISK = N'\\backup-host\mssql\<БД>\<БД>_FULL_COPY_20261118_2200.bak';
```

`FILELISTONLY` даёт логические имена файлов — они нужны для `MOVE` при восстановлении.

## 4. Проверенное восстановление

Восстанавливаем на **отдельный экземпляр** (стенд) или на тот же — но под другим именем БД и в
другие файлы. Перезапись рабочей базы запрещена.

```sql
RESTORE DATABASE [<БД>_restorecheck]
FROM DISK = N'\\backup-host\mssql\<БД>\<БД>_FULL_COPY_20261118_2200.bak'
WITH
     MOVE N'<БД>'     TO N'D:\restorecheck\<БД>_restorecheck.mdf',
     MOVE N'<БД>_log' TO N'L:\restorecheck\<БД>_restorecheck.ldf',
     RECOVERY,
     CHECKSUM,
     STATS = 5;
```

Если файлов несколько (несколько файловых групп) — по одному `MOVE` на каждый, имена берутся из
`FILELISTONLY`.

`DBCC CHECKDB` требует `db_owner` восстановленной базы (или `sysadmin`). Проверено на живой
базе (2026-11-19): restore под логином с ролью `dbcreator` выставляет `sys.databases.owner_sid`
на выполнившего restore, **но** пользователь `dbo` внутри базы наследует SID владельца из бэкапа
(источника). В результате `IS_MEMBER('db_owner')` = 0 и `DBCC CHECKDB` отказывает.

Самостоятельно выйти из этого миграционный логин не может — проверено на живой базе: серверное
право `ALTER ANY DATABASE` даёт внутри базы `ALTER ANY ROLE` / `ALTER ANY USER` (создание
объектов работает), но **не** даёт `CONTROL` над базой, а без него не проходят ни
`ALTER AUTHORIZATION` / `sp_changedbowner` (маскируются ошибкой «Cannot find the database …
or you do not have permission» при видимой в `sys.databases` базе), ни
`ALTER ROLE db_owner ADD MEMBER` (членство в фиксированных ролях меняют только `db_owner`
и `sysadmin`). Владение передаёт DBA источника (`sysadmin`) одной командой после restore. Если миграционный
логин уже имеет пользователя в восстановленной базе (типичная ситуация: логин завели в
источнике до снятия копии, и пользователь приехал из бэкапа), `ALTER AUTHORIZATION` откажет
с ошибкой «The proposed new database owner is already a user or aliased in the database» —
сначала одноимённого пользователя нужно удалить; это может сам миграционный логин
(`ALTER ANY USER` у него есть, удаление собственной учётки проходит):

```sql
-- 1. выполняет миграционный логин (DROP USER своего пользователя в копии)
USE [<БД>_restorecheck];
DROP USER migr_backup;

-- 2. выполняет DBA (sysadmin) после каждого restore-check
ALTER AUTHORIZATION ON DATABASE::[<БД>_restorecheck] TO migr_backup;
```

После `ALTER AUTHORIZATION` пользователь `dbo` перемапируется на SID нового владельца,
`IS_MEMBER('db_owner')` = 1, и `DBCC CHECKDB` проходит под миграционным логином без `sysadmin`.

Проверка целостности восстановленной копии:

```sql
DBCC CHECKDB ([<БД>_restorecheck]) WITH NO_INFOMSGS, ALL_ERRORMSGS, DATA_PURITY;
```

`DBCC CHECKDB` на большой базе идёт долго; его результат — единственное доказательство, что
копия пригодна. Если проверка не проходит, копия непригодна, и работы не начинаются.

Сверка «та же база или нет» — минимальный набор:

```sql
USE [<БД>_restorecheck];
SELECT COUNT_BIG(*) AS tables FROM sys.tables WHERE is_ms_shipped = 0;
SELECT SUM(p.rows) AS rows_total
FROM sys.partitions p JOIN sys.tables t ON t.object_id = p.object_id
WHERE t.is_ms_shipped = 0 AND p.index_id IN (0,1);
SELECT DATABASEPROPERTYEX(DB_NAME(),'Collation') AS collation_name;
```

Эти три значения сверяются с источником; расхождение означает, что восстановлена не та копия.

После проверки:

```sql
ALTER DATABASE [<БД>_restorecheck] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
DROP DATABASE [<БД>_restorecheck];
```

Решение «оставить стенд или удалить» принимается в протоколе: если на этой же копии будет
проходить пилот (этап 8), она не удаляется, а переименовывается в стендовую.

## 5. Экспорт схемы и объектов

Копия базы — не единственный артефакт: нужен читаемый текст схемы, чтобы на этапе 4 разбирать
типы и ограничения, а на этапе 9 сверять структуру.

### 5.1. DACPAC (рекомендуется как первичный артефакт)

`sqlpackage` (DACFx) снимает схему целиком, включая программируемые объекты:

```bat
sqlpackage /Action:Extract ^
  /SourceConnectionString:"Server=<сервер>;Database=<БД>;Integrated Security=true;TrustServerCertificate=true" ^
  /TargetFile:"<каталог-миграции>\<БД>\schema\<БД>_20261118.dacpac" ^
  /p:VerifyExtraction=true
```

Проверка содержимого: dacpac — это zip-архив (внутри `model.xml`); читаемый SQL-скрипт схемы
получается выгрузкой скрипта развёртывания в пустую базу:

```bat
sqlpackage /Action:Script ^
  /SourceFile:"<каталог-миграции>\<БД>\schema\<БД>_20261118.dacpac" ^
  /TargetConnectionString:"Server=<сервер>;Database=<БД>_empty;Integrated Security=true;TrustServerCertificate=true" ^
  /OutputFile:"<каталог-миграции>\<БД>\schema\<БД>_20261118_schema.sql"
```

`<БД>_empty` — пустая база, создаваемая на время проверки (скрипт развёртывания в неё — это
полный DDL). Важно: у `/Action:Script` параметр `/TargetFile:` принимает только `.dacpac`,
а не `.sql` — SQL-скрипт пишется в `/OutputFile:`.

### 5.2. SMO-скрипты (человекочитаемый SQL)

```powershell
Import-Module SqlServer   # модуль не входит в комплект Windows/SQL Server: Install-Module SqlServer

$serverName = '<сервер>'
$dbName     = '<БД>'
$outDir     = "<каталог-миграции>\$dbName\schema"
New-Item -ItemType Directory -Force -Path $outDir | Out-Null

$server   = New-Object Microsoft.SqlServer.Management.Smo.Server $serverName
$db       = $server.Databases[$dbName]
$scripter = New-Object Microsoft.SqlServer.Management.Smo.Scripter $server
$o = $scripter.Options
$o.ScriptDrops       = $false
$o.WithDependencies  = $true
$o.Indexes           = $true
$o.Triggers          = $true
$o.Permissions       = $true
$o.SchemaQualify     = $true
$o.IncludeHeaders    = $false
$o.ToFileOnly        = $true
$o.AppendToFile      = $false
$o.AnsiFile          = $true

$groups = [ordered]@{
  '01-tables.sql' = $db.Tables        # DML-триггеры попадут сюда (Options.Triggers = $true)
  '02-views.sql'  = $db.Views
  '03-procs.sql'  = $db.StoredProcedures
  '04-funcs.sql'  = $db.UserDefinedFunctions
  '05-ddl-triggers.sql' = $db.Triggers   # только DDL-триггеры уровня БД
}

foreach ($g in $groups.GetEnumerator()) {
  if ($g.Value.Count -eq 0) { continue }
  $o.FileName = Join-Path $outDir $g.Key
  $scripter.Script($g.Value)
  Write-Host ("{0}: {1} objects" -f $g.Key, $g.Value.Count)
}
```

Последовательности (`sys.sequences`) в SMO представлены коллекцией `$db.Sequences` в новых
версиях библиотеки; если коллекция недоступна — выгрузить их запросом из 13.1 (`08-identity-sequences.csv`)
и записать как ручной артефакт. То же для синонимов.

### 5.3. Задания Agent и прочие объекты вне базы

```sql
-- текст шагов заданий, привязанных к базе
USE msdb;
SELECT j.name, s.step_id, s.subsystem, s.command
FROM dbo.sysjobs j JOIN dbo.sysjobsteps s ON s.job_id = j.job_id
WHERE s.command LIKE '%<БД>%'
ORDER BY j.name, s.step_id;
```

Пакеты SSIS и прочие внешние интеграции фиксируются в инвентаре (13.1) и копируются штатными
средствами своих подсистем; в этом проекте они не переносятся pgloader.

## 6. Права и настройки соединений

Права уже сняты в 13.1 (`16-permissions.csv`, `17-roles.csv`, `18-logins.csv`) — здесь они
дополняются тем, что влияет на подключение приложений.

```sql
-- конфигурация экземпляра
SELECT name, value, value_in_use, is_dynamic, is_advanced, description
FROM sys.configurations
ORDER BY name;

-- служба, учётные записи, режим
SELECT servicename, startup_type_desc, status_desc, service_account, is_clustered, cluster_nodename
FROM sys.dm_server_services;

-- прослушиваемые порты и адреса
SELECT ip_address, port, type_desc, state_desc
FROM sys.dm_tcp_listener_states;

-- шифрование (TDE и сертификаты); запрос выполняется в контексте master:
-- в пользовательской БД dm_database_encryption_keys возвращает пусто.
-- Колонка называется encryption_state (int), не encryption_state_desc:
-- 1 = ключа нет, 3 = база зашифрована, 5 = расшифровывается, 2/6 = смена состояния
USE master;
SELECT DB_NAME(database_id) AS db, encryption_state, key_algorithm, key_length
FROM sys.dm_database_encryption_keys;

SELECT name, pvt_key_encryption_type_desc, expiry_date, subject
FROM sys.certificates
WHERE name NOT LIKE '##%';

-- linked servers
SELECT name, product, provider, data_source, is_linked, is_remote_login_enabled
FROM sys.servers
WHERE is_linked = 1;
```

Отдельно выгружаются (не через T-SQL):

- **клиентские псевдонимы** (реестр `HKLM\SOFTWARE\Microsoft\MSSQLServer\Client\ConnectTo`) —
  приложения могут ходить не по имени сервера, а по псевдониму;
- **DNS-имена, порты, правила firewall** между приложением и сервером — иначе после переключения
  «база работает, а приложение не подключается»;
- **SPN и Kerberos** (`setspn -L <учётная запись службы>`), если используется Windows-аутентификация;
- **строки подключения приложений** — как есть, но без паролей: пароли в файл не пишутся.

## 8. Хранение копии

- Копия не перезаписывается и не удаляется до подписания приёмки (раздел 10 плана).
- Хранится вне сервера источника (отдельный том, сетевое хранилище), минимум в двух местах,
  если объём позволяет.
- Доступ ограничен: копия содержит данные заказчика. Шифрование на уровне носителя или
  хранилища — по регламенту.
- В публичный репозиторий не попадают ни копии, ни DACPAC, ни скрипты схемы с именами объектов
  заказчика (см. `.gitignore` репозитория).

## Готово, когда

- [ ] полная копия снята с `COPY_ONLY`, `COMPRESSION`, `CHECKSUM`;
- [ ] `RESTORE VERIFYONLY` прошёл;
- [ ] восстановление на отдельный экземпляр выполнено и заняло известное время;
- [ ] `DBCC CHECKDB` восстановленной копии прошёл без ошибок;
- [ ] счётчики строк, число таблиц и collation восстановленной базы совпали с источником;
- [ ] DACPAC и SQL-скрипты схемы сохранены и открываются;
- [ ] права, роли, логины, задания, конфигурация, порты, шифрование и псевдонимы зафиксированы;
- [ ] протокол раздела 7 заполнен, известны дата и `last_lsn` копии;
- [ ] артефакты лежат вне репозитория, доступ к ним ограничен.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `VERIFYONLY` проходит, база не восстанавливается | проверялись только страницы, а не логика восстановления | всегда делать пробное восстановление (раздел 4) |
| бэкап «сломал» цепочку дифференциальных копий | забыт `COPY_ONLY` при работающем регламенте бэкапов | `COPY_ONLY` для всех ручных копий на живой системе |
| восстановление падает на `MOVE` | логические имена файлов не совпали | взять имена из `RESTORE FILELISTONLY` |
| копия записалась, но при проверке ошибки контрольных сумм | сетевой сбой или диск | повторить бэкап, проверить том, никогда не считать «зелёным» непроверенную копию |
| `DBCC CHECKDB` падает на восстановленной копии | повреждение в источнике | зафиксировать как проблему данных до начала миграции, эскалировать владельцу |
| «User does not have permission to run DBCC checkdb» на восстановленной копии | `dbo` наследует SID владельца источника; `owner_sid` в `sys.databases` при этом указывает на выполнившего restore | передать владение: `ALTER AUTHORIZATION` от `sysadmin` (раздел 4); `ALTER ANY DATABASE` для этого недостаточно — нужно `CONTROL` над базой |
| «The proposed new database owner is already a user or aliased in the database» | у нового владельца есть пользователь в восстановленной базе (приехал из бэкапа источника) | сначала `DROP USER` этого пользователя (может сам миграционный логин), затем повторить `ALTER AUTHORIZATION` (раздел 4) |
| схема выгружена не полностью | `WithDependencies` без `Indexes`/`Triggers`/`Permissions` | использовать настройки из 5.2 и сверять с инвентарём 13.1 по количеству объектов |
| после переключения приложение не подключается | потеряны псевдонимы/DNS/порт/SPN | фиксировать раздел 6 всегда, а не по остаточному принципу |
