# 13.6 Установка и настройка pgloader

Инструкция к этапу 7 плана. Результат этапа: pgloader нужной версии установлен на согласованном
хосте, доступ к MSSQL и к целевой БД проверен, учётные записи с минимальными правами созданы,
пароли не лежат в командной строке и в загрузочном файле, `--dry-run` проходит.

## 1. Установка

pgloader устанавливается пакетом из репозитория ОС:

```bash
sudo apt install pgloader          # Debian/Ubuntu/Astra; для другой ОС — аналогичная команда
pgloader --version
```

Версия записывается в протокол этапа и должна совпадать на стенде и в проде — иначе пилот ничего
не доказывает. Пакетный pgloader подключается к MSSQL через FreeTDS: для корректной кириллицы в
`~/.freetds.conf` должно быть `client charset = UTF-8` (без него кириллица приедет в cp1251 и
превратится в мусор на стороне UTF-8 базы; см. «Типичные ошибки»). Утилита `tsql` для проверок
соединения — пакет `freetds-bin`.

## 2. Сетевые требования и размещение

- TCP от хоста pgloader к MSSQL (`1433` или порт именованного экземпляра) и к целевой БД (`5432`).
- `nc -vz 10.10.10.20 1433`, `nc -vz 10.10.20.10 5432`, `psql ... -c 'select 1'`,
  `tsql ... -D source_db` — четыре проверки до начала работ.
- Хост pgloader ставится так, чтобы объём данных шёл по короткому маршруту: pgloader читает
  источник и пишет приёмник одновременно, поэтому важны оба направления.
- Диск под `--root-dir` (по умолчанию `/tmp/pgloader`): там копятся батчи, логи и `reject.dat`.
  Минимум — несколько гигабайт; при больших LOB — десятки.

## 3. Учётные записи и права

| Сторона | Учётная запись | Права |
|---|---|---|
| MSSQL | `migr_ro` | `db_datareader` + `VIEW DEFINITION` (без второго pgloader не прочитает каталог), `SQLAgentReaderRole` не нужен |
| Tantor | `migr_etl` | владелец целевой схемы: `CREATE`, `USAGE`, вставка, создание индексов и ограничений (13.5) |

`sa` и `postgres` не используются. Прав на запись в MSSQL быть не должно — это гарантия, что
миграция не изменит источник.

## 4. Пароли: env и mustache, а не текст в файле

pgloader поддерживает подстановку переменных окружения через mustache-шаблоны, поэтому
загрузочный файл может лежать в репозитории без секретов:

```
LOAD DATABASE
     FROM mssql://{{MSSQL_USER}}:{{MSSQL_PWD}}@{{MSSQL_HOST}}:1433/{{MSSQL_DB}}
     INTO postgresql://{{PG_USER}}@{{PG_HOST}}:5432/{{PG_DB}}
     ...
```

```bash
export MSSQL_USER=migr_ro MSSQL_HOST=10.10.10.20 MSSQL_DB=source_db
export PG_USER=migr_etl PG_HOST=10.10.20.10 PG_DB=target_db
export MSSQL_PWD="$(cat /run/secrets/mssql_migr_ro)"
export PGPASSFILE=/home/pgloader/.pgpass     # пароль приёмника — в файле с правами 600
chmod 600 /home/pgloader/.pgpass

pgloader --verbose --logfile /var/log/pgloader/migrate.log ms.load
```

Альтернатива для неинтерактивных прогонов — INI-файл контекста:

```ini
# /etc/pgloader/target.ini   (chmod 600, вне репозитория)
MSSQL_PWD = <пароль>
PG_USER   = migr_etl
```

```bash
pgloader --context /etc/pgloader/target.ini ms.load
```

Правила, которые не обсуждаются:

- пароль не передаётся аргументом командной строки (`-P`, `--password` в URL на виду в `ps` и в
  истории shell);
- `.pgpass` — `600`, владелец — учётная запись, под которой работает pgloader;
- лог pgloader (`--logfile`) имеет ограниченные права: в него попадает строка подключения —
  проверить после первого прогона, что пароль не выводится целиком;
- загрузочный файл с `{{...}}` безопасно хранить в репозитории, файл с реальным паролем — нет.

## 5. Проверка до начала загрузки

```bash
# 1. версия и зависимости
pgloader --version
ldd "$(command -v pgloader)" | grep -Ei 'sybdb|freetds'   # для 3.6.x

# 2. синтаксис загрузочного файла без выполнения
pgloader --dry-run --verbose ms.load

# 3. доступ к источнику на уровне каталога (не только сети)
tsql -H "$MSSQL_HOST" -p 1433 -U "$MSSQL_USER" -D "$MSSQL_DB" <<'SQL'
select count(*) from sys.tables where is_ms_shipped = 0;
go
SQL

# 4. доступ к приёмнику
psql "host=$PG_HOST dbname=$PG_DB user=$PG_USER" -c "select current_user, current_database();"
```

Без `-P` tsql сам запросит пароль интерактивно — отдельного env-механизма пароля у tsql нет, и для
неинтерактивной проверки это единственный вариант без пароля в командной строке.

`--dry-run` печатает, какие команды pgloader собирается выполнить в PostgreSQL: это единственный
способ увидеть результат правил `CAST` и переименований до того, как они применятся.

## Готово, когда

- [ ] версия pgloader зафиксирована и совпадает со стендовой;
- [ ] установка воспроизводима (команды сохранены в протоколе или в скрипте);
- [ ] `tsql` или JDBC-подключение к источнику работает, кириллица читается корректно;
- [ ] `psql` к приёмнику работает под ролью миграции;
- [ ] учётные записи с минимальными правами созданы, `sa`/`postgres` не используются;
- [ ] пароли только в env/INI/`.pgpass`, права `600`, в истории shell и в репозитории их нет;
- [ ] `--dry-run` загрузочного файла проходит без ошибок синтаксиса;
- [ ] место под `--root-dir` достаточно, логи пишутся в отдельный каталог.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `Connection to the database failed for an unknown reason` | FreeTDS/TDS-версия, порт именованного экземпляра, TLS | проверить `tsql` с теми же параметрами; `tds version = 7.4`; указать порт явно |
| кириллица превращается в мусор | нет `client charset = UTF-8` | добавить в `~/.freetds.conf`, перезапустить прогон |
| pgloader видит таблицы, но не видит колонок/индексов | у учётной записи нет `VIEW DEFINITION` | выдать право, не `db_owner` |
| пароль в логе | `--verbose` печатает строку подключения | ограничить права на лог, использовать env/INI, не держать `--debug` в проде |
| `--dry-run` падает на `CAST` | неверный синтаксис правила | сверять с разделом 13.4: `{drop|keep} typemod`, `when (= precision -1)` |
| прогон идёт, но медленно и с `swapping` | мало RAM под `prefetch rows` | уменьшить `prefetch rows`/`batch rows`, смотреть `vmstat` |
