# 13.10 Валидация результата

Инструкция к этапу 10 плана. Результат: доказанное соответствие структуры и данных снимку T-0,
проверенная функциональность и производительность, заполненный протокол с pass/fail по каждому
пункту и подписанная приёмка.

База сравнения — **снимок T-0** (13.3), а не снимок этапа 3: между ними база могла меняться.

## 1. Уровни проверки

| Уровень | Что доказывает | Инструмент |
|---|---|---|
| структура | перенесены все объекты и с ожидаемыми свойствами | каталог PostgreSQL против инвентаря |
| данные: количество | ни одна строка не потеряна и не задвоена | счётчики из `--summary` и `count(*)` |
| данные: агрегаты | значения не подменены, не обрезаны, не сдвинуты | `31-aggregates.csv` против своего аналога в PG |
| данные: содержимое | побайтовое совпадение критичных таблиц | упорядоченная выгрузка + SHA-256 |
| функциональность | запросы приложения дают те же результаты | набор эталонных запросов |
| производительность | планы и время приемлемы | `EXPLAIN (ANALYZE, BUFFERS)`, `pg_stat_statements` |

## 2. Структура

```sql
-- объекты по типам (сверить с inventory.md)
SELECT c.relkind, count(*)
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'app' GROUP BY c.relkind ORDER BY 1;
```

Отдельно проверяются свойства, из-за которых «данные есть, а работать нельзя»:

```sql
-- колонки с типами, отличными от решений 13.4
SELECT table_name, column_name, data_type, character_maximum_length, numeric_precision, numeric_scale
FROM information_schema.columns
WHERE table_schema = 'app'
ORDER BY table_name, ordinal_position;

-- ограничения и их валидность
SELECT conname, contype, convalidated FROM pg_constraint k
JOIN pg_namespace n ON n.oid = k.connamespace WHERE n.nspname = 'app' ORDER BY 2, 1;

-- непригодные индексы (пустой результат обязателен; план 8.3)
SELECT n.nspname, c.relname AS index_name, i.indisvalid, i.indisready
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'app' AND NOT (i.indisvalid AND i.indisready);

-- идентичность
SELECT table_name, column_name, identity_generation, identity_start, identity_increment
FROM information_schema.columns
WHERE table_schema = 'app' AND is_identity = 'YES';

-- права: приложение должно иметь только DML
SELECT grantee, privilege_type, count(*)
FROM information_schema.role_table_grants
WHERE table_schema = 'app' GROUP BY 1, 2 ORDER BY 1, 2;
```

Проверка целостности btree-индексов и куч — `pg_amcheck` (план 8.3; расширение `amcheck`
устанавливается в 13.9; пароль tsql при выгрузках запрашивается интерактивно):

```bash
pg_amcheck --database=target_db --heapallindexed --parent-check
```

## 3. Количество строк

Три источника должны сойтись:

1. `--summary` pgloader (что он думает, что перенёс);
2. `count(*)` в PostgreSQL (что реально лежит);
3. `30-rowcounts.csv` снимка T-0.

```sql
SELECT relname, n_live_tup FROM pg_stat_user_tables
WHERE schemaname = 'app' ORDER BY n_live_tup DESC;   -- быстро, но оценка

SELECT count(*) FROM app.orders;                      -- точно, но дорого
```

Для критичных таблиц — точный `count(*)`; для остальных допустимо `n_live_tup` после `ANALYZE`,
и расхождение с T-0 объясняется отдельной строкой протокола.

## 4. Агрегаты: как сравнивать на самом деле

Формат `object_name;metric;value` из 13.3 повторяется на стороне PostgreSQL теми же метриками.
Три правила, без которых сравнение ложно:

**4.1. Числа.** На стороне MSSQL агрегаты снимаются как `decimal(38,6)`; в PostgreSQL сумму надо
привести к тому же виду, иначе `1234.5` не совпадёт с `1234.500000`:

```sql
SELECT 'app.orders' AS object_name, 'sum.total' AS metric,
       to_char(sum(total), 'FM999999999999999990.000000') AS value
FROM app.orders;
```

**4.2. Даты — только через epoch.** Строковое представление дат между СУБД не совпадает (разное
число знаков дробной части, разные форматы), поэтому `min`/`max` дат сравниваются как целые числа
секунд от 1970-01-01:

```sql
-- PostgreSQL: секунды эпохи (для timestamp без зоны считаем его UTC)
SELECT 'app.orders' AS object_name, 'min.created_at' AS metric,
       floor(extract(epoch FROM (min(created_at) AT TIME ZONE 'UTC')))::bigint::text AS value
FROM app.orders;
```

`floor()` обязателен: `::bigint` усекает к нулю, а `DATEDIFF_BIG` считает границы секунд — на
датах до 1970 с дробной частью они разошлись бы на 1.

```sql
-- MSSQL (для снимка, если он ещё не снят в таком виде)
SELECT DATEDIFF_BIG(SECOND, CAST('19700101' AS datetime2), MIN(created_at)) AS min_epoch
FROM dbo.Orders;
```

Если снимок 13.3 уже сохранён строкой, даты переснимаются в epoch — это уточнение к 13.3, а не
повод «сравнивать на глаз».

**4.3. `float` не сравнивается.** Колонки `float`/`real` присутствуют только как `count`/`nulls`:
сумма плавающих значений зависит от порядка сложения и нестабильна между СУБД.

Сравнение файлов:

```powershell
$src = Import-Csv '<каталог-миграции>\<БД>\snapshot\T0-2026-11-19\31-aggregates.csv' -Delimiter ';'
$dst = Import-Csv '<каталог-миграции>\<БД>\out\t0-aggregates.csv' -Delimiter ';'
Compare-Object $src $dst -Property object_name, metric, value -PassThru | Format-Table -AutoSize
```

```bash
diff -u <(sort snapshot/T0-2026-11-19/31-aggregates.csv) <(sort out/t0-aggregates.csv)
```

Допустимое расхождение — ноль. Любое отличие попадает в протокол с классификацией: тип, пустые
значения, кодировка, даты, денежные суммы.

## 5. Побайтовая сверка критичных таблиц

Для 5–10 таблиц, где ошибка дороже всего (финансовые регистры, договоры, остатки), выполняется
полная сверка по правилам нормализации 13.3, раздел 7.

PostgreSQL:

```bash
psql -d target_db -At -F $'\t' -c "
  SELECT id, customer_id, to_char(created_at,'YYYY-MM-DD\"T\"HH24:MI:SS.US'),
         to_char(total,'FM999999999999999990.0000'), status
  FROM app.orders ORDER BY id" > orders.pg.tsv
sha256sum orders.pg.tsv
```

MSSQL (тем же порядком колонок и теми же форматами):

```bash
printf "SET NOCOUNT ON;\nSELECT id, customer_id, CONVERT(varchar(30), created_at, 126),
  CAST(total AS decimal(19,4)), status FROM dbo.Orders ORDER BY id;\ngo\n" \
 | tsql -H "$MSSQL_HOST" -U "$MSSQL_USER" -D "$MSSQL_DB" > orders.ms.txt
```

Различия форматов (`126` даёт 3 или 7 знаков дробной части, `to_char` — столько, сколько задано)
устраняются приведением обеих выгрузок к одной форме одним и тем же скриптом нормализации, а не
правкой глазами. Хеши сравниваются как строки, имена файлов хешей — `33-hashes/` снимка.

## 6. Функциональность

Набор эталонных запросов собирается до миграции из реальной практики (5–15 штук), с ожидаемым
результатом на источнике:

| Тип | Пример | Что ловит |
|---|---|---|
| точечный поиск | `where number = '...'` | регистр, пробелы, кодировка |
| поиск по подстроке | `like '%иванов%'` | collation, `ё`, `ILIKE` |
| диапазон по датам | `created_at between ...` | сдвиг часового пояса |
| агрегат по группе | `sum(total) by month` | округление, `money` → `numeric` |
| соединение 3–4 таблиц | отчёт | планы, индексы |
| сортировка справочника | `order by name` | порядок кириллицы |
| пейджинг | `limit/offset` (был `TOP`) | корректность `ORDER BY` |

Результаты сравниваются построчно. Расхождения объясняются **до** приёмки: «сортировка отличается,
потому что collation ICU, приложение сортирует по-своему» — валидное объяснение; «отличается
сумма» — нет.

## 7. Производительность

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT ... ;   -- 5–10 самых тяжёлых запросов из инвентаря (13.1, раздел 14)
```

На что смотреть:

- нет ли `Seq Scan` по большой таблице там, где в MSSQL был seek;
- нет ли `external merge Disk` (мало `work_mem` для отчёта);
- оценка строк (`rows=`) против факта — признак устаревшей статистики;
- время выполнения сравнивается с источником с заранее согласованным допуском (например, ±30%);
  «в PostgreSQL медленнее» без числа — не аргумент.

```sql
SELECT queryid, calls, mean_exec_time, total_exec_time, rows
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

## 8. Протокол валидации

| Проверка | Критерий | Результат | Комментарий |
|---|---|---|---|
| Объекты по типам | совпадает с инвентарём | pass/fail | расхождения перечислены |
| Типы колонок | соответствуют 13.4 | pass/fail | |
| Ограничения, `convalidated` | все true | pass/fail | |
| Identity и последовательности | `setval` по max, вставка проходит | pass/fail | |
| Счётчики строк | разница 0 | pass/fail | |
| Агрегаты | разница 0 | pass/fail | |
| Хеши критичных таблиц | совпали | pass/fail | список таблиц |
| Эталонные запросы | результаты идентичны | pass/fail | |
| Планы запросов | нет деградации сверх допуска | pass/fail | |
| Права приложения | DML есть, DDL нет | pass/fail | |

Протокол подписывается владельцем системы (этап 0/1 плана). Без подписи переключение (13.12) не
выполняется.

## Готово, когда

- [ ] структура сверена с инвентарём, расхождения перечислены и объяснены;
- [ ] счётчики строк совпали со снимком T-0;
- [ ] агрегаты совпали, даты сравнивались в epoch, `float` исключён;
- [ ] хеши 5–10 критичных таблиц совпали;
- [ ] эталонные запросы дали идентичные результаты, расхождения объяснены;
- [ ] планы и время тяжёлых запросов сняты, деградация в пределах допуска;
- [ ] протокол заполнен и подписан владельцем системы.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| суммы «не сходятся» на 0.000001 | разное число знаков при выводе | `to_char` с фиксированным масштабом с обеих сторон |
| даты не сравниваются | строковый формат различается | сравнивать epoch-секунды |
| счётчики совпали, а бизнес-отчёт нет | логика запроса, а не данные | разобрать конкретный запрос, не откладывать |
| «все таблицы сходятся», кроме одной, где строки на 1% больше | повторный прогон без `truncate` | перезалить таблицу целиком |
| запросы медленнее в 10 раз | нет статистики/индексов | `ANALYZE`, проверить индексы, планы |
| проверка сделана до остановки записи | источник менялся после снимка | переснять T-0 и повторить сверку |
