# 13.11 Дельта изменений

Инструкция к этапу 12 плана и разделу 5.3 («вариант B»). Применяется только если запись в источник
нельзя остановить на время переноса основного объёма.

Ключевая оговорка, которую надо озвучить до начала: **нативной репликации MSSQL → PostgreSQL не
существует**. Всё, что ниже, — либо свой механизм поверх CDC, либо отдельная инфраструктура
(Debezium), либо повторная перезагрузка изменённых таблиц. Выбор фиксируется письменно, потому что
у каждого варианта своя цена и свои дырки.

## 1. Выбор механизма

| Механизм | Что даёт | Цена | Ограничения |
|---|---|---|---|
| MSSQL CDC + свой аппликатор | построчные изменения (insert/update/delete), порядок по LSN | скрипт на 100–300 строк, поддержка на время проекта | CDC включает запись в источник, требует Agent, меняет БД |
| Debezium (SQL Server connector) + JDBC sink | промышленный поток изменений, повторы, метрики | Kafka/Connect, отдельная эксплуатация | требует CDC на источнике; маппинг типов настраивается вручную |
| Повторная перезагрузка таблиц | ничего не надо программировать | окно на каждую «горячую» таблицу | **не видит DELETE**; годится только для append-only/soft-delete таблиц |
| Полный повторный прогон pgloader в окно | самый простой и надёжный | окно ≥ полного прогона | противоречит цели «без простоя», но иногда это и есть решение |

Правило выбора: если окно останова ≤ времени полного прогона — берётся вариант A (13.8) и дельта не
нужна вовсе. Дельта вводится только тогда, когда полный прогон в окно не влезает.

## 2. Точка старта: снимок и LSN

Порядок, который нельзя нарушать:

1. **Включить CDC до снятия снимка** — иначе изменения, сделанные между снимком и включением CDC,
   потеряны безвозвратно.
2. Снять снимок T-0 и выполнить полную загрузку (13.3, 13.8).
3. Зафиксировать LSN, соответствующий состоянию данных на момент снимка:
   - если снимок делался по копии базы — `last_lsn` из `msdb.dbo.backupset` (13.2);
   - если по живой базе — `sys.fn_cdc_get_max_lsn()` непосредственно перед началом чтения таблиц
     pgloader (и записать время в протокол).

Дальше аппликатор читает изменения **только с этого LSN**: всё, что раньше, уже есть в данных.

## 3. Включение CDC на источнике

Требуется `sysadmin` и запущенный SQL Server Agent (задания `cdc.*` собирают изменения из журнала).

> **Предупреждение.** Включение CDC — это изменение боевой базы: появляются объекты, задания и
> дополнительная нагрузка. Решение согласовывается с владельцем источника и DBA заранее; на
> таблицах с критичной задержкой записи включение CDC предварительно измеряется на стенде.

```sql
-- 1. на уровне базы
EXEC sys.sp_cdc_enable_db;

-- 2. на уровне таблицы (по каждой таблице, которая меняется)
EXEC sys.sp_cdc_enable_table
     @source_schema        = N'dbo',
     @source_name          = N'Orders',
     @role_name            = N'cdc_reader',      -- роль только на чтение изменений
     @supports_net_changes = 1;

-- 3. проверка
SELECT ct.capture_instance, ct.start_lsn, ct.create_date, OBJECT_NAME(ct.source_object_id) AS tbl
FROM cdc.change_tables ct;

SELECT job_id, job_type, job_description FROM msdb.dbo.cdc_jobs;

-- 4. текущая позиция и задержка
SELECT sys.fn_cdc_get_max_lsn() AS max_lsn,
       sys.fn_cdc_map_lsn_to_time(sys.fn_cdc_get_max_lsn()) AS max_lsn_time;
```

Что важно знать до включения (риски и ограничения):

- CDC **увеличивает** журнал и нагрузку: появляется capture job, который читает лог, и таблицы
  `cdc.<capture_instance>_CT`, которые растут;
- если capture job останавливается или не успевает, **обрезка журнала транзакций задерживается** —
  возможен рост лога до исчерпания диска; мониторинг `cdc_jobs` обязателен на всё время работы;
- ретенция по умолчанию — 3 дня (`sp_cdc_change_job @job_type='cleanup'`, `@retention`). Если
  миграция длиннее, изменения будут удалены до того, как их прочтут. Ретенцию увеличивают заранее;
- cleanup-задание удаляет до 5000 строк за цикл — при больших объёмах изменений фактическая
  ретенция достигается не мгновенно;
- CDC **не фиксирует `TRUNCATE TABLE`** — только DML. Если приложение чистит таблицы `TRUNCATE`,
  этот вариант дельты неполон;
- `@supports_net_changes = 1` требует на таблице первичного ключа или уникального индекса —
  иначе `sp_cdc_enable_table` упадёт (ошибка 22939); для таблиц без ключа остаётся только
  `@supports_net_changes = 0` (полный поток изменений);
- CDC доступен в Standard-редакции только с SQL Server 2016 SP1 (раньше — только Enterprise);
  для старых Standard-серверов вариант дельты меняется;
- изменение схемы таблицы (добавление/удаление колонки) ломает чтение `fn_cdc_get_all_changes_*`;
  такие изменения на время миграции запрещаются регламентом;
- включение CDC создаёт в БД схему `cdc` и системные объекты — это изменение источника, требует
  согласования с владельцем.

## 4. Чтение изменений

```sql
DECLARE @from binary(10) = sys.fn_cdc_get_min_lsn(N'dbo_Orders'),  -- или зафиксированный LSN
        @to   binary(10) = sys.fn_cdc_get_max_lsn();

SELECT __$start_lsn, __$seqval, __$operation,
       __$update_mask,
       id, customer_id, status, total, created_at, updated_at
FROM cdc.fn_cdc_get_all_changes_dbo_Orders(@from, @to, N'all update old')
ORDER BY __$start_lsn, __$seqval;
```

Коды `__$operation`: `1` — delete, `2` — insert, `3` — before update, `4` — after update.
Порядок применения — строго по `__$start_lsn`, затем `__$seqval`; `all update old` нужен, если
аппликатору требуется предыдущее значение колонки (например, для аудита).

Выборка делается пакетами (по LSN-диапазонам), результат складывается в файл/таблицу на стороне
pgloader-хоста. Каждый пакет сопровождается «водяным знаком» (`@to`), чтобы после сбоя продолжить
с этого места.

## 5. Применение в PostgreSQL

Идемпотентный «upsert» по первичному ключу, чтобы повторное применение пакета ничего не ломало:

```sql
INSERT INTO app.orders (id, customer_id, status, total, created_at, updated_at)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (id) DO UPDATE
   SET customer_id = EXCLUDED.customer_id,
       status      = EXCLUDED.status,
       total       = EXCLUDED.total,
       created_at  = EXCLUDED.created_at,
       updated_at  = EXCLUDED.updated_at;
```

Порядок и идемпотентность обеспечивает LSN, а не бизнес-поля: пакет применяется один раз по
водяному знаку применённого LSN, повторная выгрузка того же пакета ничего не меняет (upsert
идемпотентен), следующий пакет читается со следующего LSN. Guard по `updated_at` недопустим:
колонка бывает `NULL`, не обновляется в апдейте или «уезжает назад» — такие изменения молча
теряются.

Правила применения:

- одна транзакция на пакет одного LSN-диапазона: частично применённый пакет ломает согласованность
  ссылок;
- внутри пакета операции применяются **в LSN-порядке с чередованием** insert/update и delete
  (либо по ключу вычисляется чистый эффект — последняя операция по ключу выигрывает). Порядок
  «сначала все upsert, потом все delete» ошибочен: цикл delete → повторный insert того же ключа
  оставит строку удалённой, хотя в источнике она существует. Поведение FK (`ON DELETE CASCADE`)
  учитывается при вычислении чистого эффекта;
- `session_replication_role = replica` отключает **в том числе триггеры FK**: ссылочная
  целостность во время применения дельты не проверяется. Сверка FK после применения обязательна
  (`VALIDATE CONSTRAINT`, 13.9) и фиксируется в протоколе;
- триггеры на приёмнике на время применения дельты отключаются (`session_replication_role =
  replica` под суперпользователем) либо пишутся идемпотентно — иначе аудит задвоится;
- после применения дельты последовательности снова выставляются по `max(id)` (13.9, раздел 5):
  аппликатор вставляет явные идентификаторы;
- `ON CONFLICT` требует первичного ключа/уникального индекса — если в источнике ключа нет, вариант
  дельты неприменим.

## 6. Debezium: когда он оправдан

Если миграций впереди несколько или поток изменений нужен дольше одного окна, вместо своего
аппликатора ставится Debezium:

- SQL Server connector читает CDC-таблицы (значит, CDC включается так же, как в разделе 3);
- приёмник — JDBC sink connector с `insert.mode=upsert`, `pk.mode=record_key`;
- типы маппируются явно (`decimal.handling.mode`, `time.precision.mode`), иначе даты/деньги
  поедут;
- цена: Kafka + Kafka Connect + мониторинг лага; это отдельная система, которую кто-то должен
  эксплуатировать после миграции.

## 7. Повторная перезагрузка изменённых таблиц

Самый дешёвый вариант и самый ограниченный. Реализуется через `MATERIALIZE VIEWS` (13.7):

```
 MATERIALIZE VIEWS orders_delta AS $$
   select * from dbo.Orders where UpdatedAt >= '2026-11-19T22:00:00'
 $$
```

Ограничения, которые надо проговорить:

- удаления не переносятся: строка, удалённая в источнике, останется в приёмнике. Допустимо только
  для таблиц без `DELETE` или с soft-delete;
- фильтр по `UpdatedAt` работает, только если колонка действительно обновляется при каждом
  изменении (проверяется на пилоте: обновить строку и посмотреть, выросла ли метка);
- перезагрузка «горячей» таблицы целиком в окне может оказаться дольше, чем весь остальной простой.

## 8. Окно переключения с дельтой

```
T-60  pre-flight (13.8), проверка, что CDC догоняет: max_lsn_time ≈ now()
T-30  остановка записи в приложении
T-30  зафиксировать финальный LSN
T-25  применить последний пакет дельты
T-15  выставить последовательности (13.9), собрать ANALYZE
T-10  быстрая сверка: счётчики строк по изменённым таблицам, агрегаты
T-0   переключение приложения (13.12)
```

Если на T-25 дельта не применилась — откат окна: снять остановку записи, разобрать причину, не
переключать приложение «частично».

## 9. Проверка дельты

1. Количество операций: сумма `count(*)` по capture-таблицам с `__$start_lsn >= стартового`
   против числа применённых операций (журнал аппликатора).
2. Счётчики строк и агрегаты по изменённым таблицам — против источника на момент останова.
3. Нарушения ссылочной целостности — запросы из 13.9, раздел 3, до валидации ФК.
4. Повторное применение последнего пакета — количество строк не должно измениться (идемпотентность).

## Готово, когда

- [ ] механизм дельты выбран и обоснован, ограничения озвучены владельцу;
- [ ] CDC включён до снятия снимка, ретенция покрывает длительность миграции;
- [ ] стартовый LSN зафиксирован в протоколе и совпадает с состоянием загруженных данных;
- [ ] аппликатор идемпотентен, применяет пакеты в порядке LSN, удаления обработаны;
- [ ] триггеры на приёмнике не задваивают эффект;
- [ ] последовательности выставлены после дельты;
- [ ] дельта проверена: операции сошлись, агрегаты совпали, ФК валидны;
- [ ] окно переключения отрепетировано, в том числе сценарий «дельта не применилась».

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| часть изменений потеряна | CDC включён после снимка | включать CDC первым шагом, стартовый LSN — из снимка |
| `fn_cdc_get_all_changes_*` падает на старом LSN | ретенция вычистила данные | увеличить `@retention` заранее, читать чаще |
| в приёмнике остались удалённые строки | `TRUNCATE`/`DELETE` не учтены | использовать CDC-аппликатор, а не перезагрузку |
| после дельты вставки падают на `duplicate key` | последовательность не выставлена | `setval` после применения |
| аудит задвоился | триггеры сработали на аппликаторе | `session_replication_role = replica` или идемпотентные триггеры |
| дельта применяется «по кругу» | нет водяного знака LSN | сохранять последний применённый LSN, возобновлять с него |
| чтение изменений упало после `ALTER TABLE` в источнике | capture instance устарел | запретить DDL на время окна, при необходимости пересоздать capture instance |
