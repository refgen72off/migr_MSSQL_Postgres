# 13.9 Пост-обработка приёмника

Инструкция к этапам 9 и 12 плана. Результат: последовательности выставлены, ФК и `CHECK` созданы и
валидированы, `DEFAULT` восстановлены, триггеры и код созданы, права выданы, статистика собрана,
индексы проверены.

Порядок работ именно такой: сначала данные и целостность, потом код и права. Обратный порядок
(сначала триггеры) ломает загрузку и маскирует ошибки данных под ошибки логики.

## 1. Что pgloader сделал и что осталось

| Объект | Сделал pgloader | Делаем здесь |
|---|---|---|
| таблицы, PK, уникальные индексы, часть индексов | да (если `create tables`/`create indexes`) | проверить полноту против инвентаря |
| внешние ключи | нет (`no foreign keys`) | создать и валидировать |
| `CHECK`, `DEFAULT` | нет | создать вручную из инвентаря |
| identity / последовательности | частично: identity-колонки становятся `serial`/`bigserial` (последовательность создаётся), значение не выставлено (`reset no sequences`) | выставить `setval`; конверсия в `GENERATED AS IDENTITY` — опционально (шаг 2 раздела 5) |
| триггеры, функции, процедуры, представления | нет | создать адаптированный код |
| права, роли | нет | выдать по реестру прав |
| статистика | нет | `ANALYZE`, расширенная статистика |
| autovacuum | выключен на время загрузки (13.5) | включить |

## 2. Индексы и ограничения

Проверка, что индексы валидны и что pgloader ничего не потерял:

```sql
-- невалидные/неготовые индексы
SELECT n.nspname AS schema, c.relname AS index_name, i.indisvalid, i.indisready
FROM pg_index i
JOIN pg_class c     ON c.oid = i.indexrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'app' AND (NOT i.indisvalid OR NOT i.indisready);

-- сравнение количества индексов с инвентарём (13.1, 06-indexes.csv)
SELECT count(*) FROM pg_indexes WHERE schemaname = 'app';
```

Индексы, которых не хватает, создаются по списку из инвентаря. Для больших таблиц — с
`CONCURRENTLY` (вне транзакции) либо в окне:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_customer
    ON app.orders (customer_id);
```

Фильтрованные индексы MSSQL → частичные индексы PostgreSQL (условие переписать):

```sql
CREATE INDEX idx_orders_active ON app.orders (created_at) WHERE status <> 'closed';
```

Индексы с `INCLUDE` (покрывающие) → `INCLUDE` PostgreSQL 11+:

```sql
CREATE INDEX idx_orders_covering ON app.orders (customer_id) INCLUDE (status, total);
```

## 3. Внешние ключи: создать, но не сразу валидировать

Сначала — поиск нарушений (пустая выборка = можно создавать ФК сразу, без `NOT VALID`):

```sql
-- пример: дочерняя таблица ссылается на отсутствующего родителя
SELECT count(*) AS orphans
FROM app.order_lines l
LEFT JOIN app.orders o ON o.id = l.order_id
WHERE l.order_id IS NOT NULL AND o.id IS NULL;
```

Создание с последующей валидацией (не блокирует запись и не сканирует таблицу дважды):

```sql
ALTER TABLE app.order_lines
    ADD CONSTRAINT fk_order_lines_order
    FOREIGN KEY (order_id) REFERENCES app.orders (id)
    ON DELETE CASCADE
    NOT VALID;

ALTER TABLE app.order_lines VALIDATE CONSTRAINT fk_order_lines_order;

SELECT conrelid::regclass AS table_name, conname, convalidated
FROM pg_constraint
WHERE contype = 'f' AND NOT convalidated;
```

Пустой результат второго запроса — критерий готовности. В PostgreSQL `NO ACTION` и `RESTRICT` по
умолчанию `NOT DEFERRABLE` и проверяются в конце оператора. Разница проявляется только у
отложенных ограничений: `RESTRICT` нельзя сделать `DEFERRABLE`, а `NO ACTION` с
`DEFERRABLE INITIALLY DEFERRED` проверяется в конце транзакции. Поэтому MSSQL `NO ACTION`
переносится как `NO ACTION`; `RESTRICT` выбирается, только если нужно явно запретить отложенную
проверку.

## 4. CHECK-ограничения и уникальность с NULL

`CHECK` из инвентаря (`07-constraints.csv`) создаётся с `NOT VALID`, затем валидируется:

```sql
ALTER TABLE app.orders
    ADD CONSTRAINT ck_orders_total_positive CHECK (total >= 0) NOT VALID;

ALTER TABLE app.orders VALIDATE CONSTRAINT ck_orders_total_positive;
```

Уникальность с NULL — отдельное решение (13.4): в MSSQL уникальный индекс допускал один NULL, в
PostgreSQL — сколько угодно. Чтобы сохранить поведение:

```sql
ALTER TABLE app.users
    ADD CONSTRAINT uq_users_email UNIQUE NULLS NOT DISTINCT (email);
```

## 5. Идентичность и последовательности

1) Посмотреть, какие колонки должны быть идентификаторами (инвентарь `08-identity-sequences.csv`).

2) (опционально) Конверсия `serial` в `GENERATED AS IDENTITY`. pgloader создаёт identity-колонки
как `serial`/`bigserial` — у колонки уже есть default из последовательности, поэтому `ADD
GENERATED` напрямую упадёт. Если проектное решение 7.3 плана — `GENERATED AS IDENTITY`:

```sql
-- сначала снять default, оставшийся от serial, и убрать его последовательность:
ALTER TABLE app.orders ALTER COLUMN id DROP DEFAULT;
DROP SEQUENCE IF EXISTS app.orders_id_seq;

ALTER TABLE app.orders
    ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
```

`BY DEFAULT` — если приложение само вставляет идентификаторы (исторические данные, импорт);
`ALWAYS` — если вставки только через `DEFAULT`, и это проверено по коду. Если конверсия не
делается — колонки остаются `serial`/`bigserial`, это допустимое решение 7.3.

3) Выставить значения по максимуму данных (для пустой таблицы — `setval(..., 1, false)`, чтобы
первый `nextval` вернул 1). Генератор команд:

```sql
SELECT format('SELECT setval(%L, COALESCE((SELECT max(%I) FROM %I.%I), 1), (SELECT max(%I) IS NOT NULL FROM %I.%I));',
              pg_get_serial_sequence(format('%I.%I', n.nspname, c.relname), a.attname),
              a.attname, n.nspname, c.relname, a.attname, n.nspname, c.relname) AS cmd
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_attribute a ON a.attrelid = c.oid AND a.attnum > 0 AND NOT a.attisdropped
WHERE c.relkind = 'r' AND n.nspname = 'app'
  AND pg_get_serial_sequence(format('%I.%I', n.nspname, c.relname), a.attname) IS NOT NULL;
```

Выполнить вывод, затем проверить тестовой вставкой и откатом:

```sql
BEGIN;
INSERT INTO app.orders (customer_id, created_at) VALUES (1, now()) RETURNING id;
ROLLBACK;
```

4) Последовательности, перенесённые как отдельные объекты (`sys.sequences`), создаются вручную
(`CREATE SEQUENCE ... START WITH <current_value+increment>`) — их состояние надо взять из
`08-identity-sequences.csv`, снятого на T-0.

## 6. DEFAULT-значения

```sql
ALTER TABLE app.orders
    ALTER COLUMN created_at SET DEFAULT now(),
    ALTER COLUMN number     SET DEFAULT 'б/н';
```

Соответствия выражений — раздел 6 инструкции 13.4. Проверка полноты: сравнить число колонок с
дефолтами в источнике и в приёмнике.

```sql
SELECT table_schema, table_name, column_name, column_default
FROM information_schema.columns
WHERE table_schema = 'app' AND column_default IS NOT NULL
ORDER BY 1, 2, 3;
```

## 7. Код: триггеры, функции, представления

1) Функции и процедуры создаются из адаптированного кода (13.4, 13.13) — по зависимостям, снизу
   вверх (сначала функции, потом триггеры).
2) Триггеры создаются **после** загрузки данных, иначе они сработают на каждой вставляемой строке:

```sql
CREATE OR REPLACE FUNCTION app.trg_orders_audit() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO app.orders_audit (order_id, changed_at)
    VALUES (NEW.id, now());
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_orders_audit_ai
    AFTER INSERT ON app.orders
    FOR EACH ROW EXECUTE FUNCTION app.trg_orders_audit();
```

3) Порядок срабатывания задаётся именем триггера (сортировка по имени), а не числом — если в MSSQL
   был порядок, он воспроизводится префиксами `10_`, `20_`.
4) Состояние триггеров проверяется по `pg_trigger.tgenabled`: `O` — включён, `D` — отключён.
5) Представления создаются после таблиц; индексированные представления MSSQL → материализованные:

```sql
CREATE MATERIALIZED VIEW app.mv_orders_monthly AS
SELECT date_trunc('month', created_at) AS month, count(*) AS cnt, sum(total) AS total
FROM app.orders GROUP BY 1;

CREATE UNIQUE INDEX mv_orders_monthly_month ON app.mv_orders_monthly (month);
REFRESH MATERIALIZED VIEW CONCURRENTLY app.mv_orders_monthly;
```

Уникальный индекс обязателен для `CONCURRENTLY`; порядок обновления (по расписанию или после
загрузки) фиксируется в регламенте.

## 8. Права и владение

Права переносятся из реестра (13.1, `16`–`18`), но не «как есть»: роль заказчика в MSSQL и роль
приложения в PostgreSQL — разные сущности.

```sql
GRANT USAGE ON SCHEMA app TO app_rw;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_rw;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO app_rw;
ALTER DEFAULT PRIVILEGES FOR ROLE migr_etl IN SCHEMA app
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;
```

Проверка: приложение под своей ролью читает/пишет свои таблицы и **не** может создавать объекты
(13.5). Роли уровня кластера (`CREATEROLE`, `SUPERUSER`) не выдаются.

## 9. Статистика

```sql
-- 1. базовый сбор
VACUUM (ANALYZE) app.orders;

-- 2. повышенная детализация для колонок с перекосом
ALTER TABLE app.orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE app.orders (status);

-- 3. расширенная статистика для коррелированных колонок
CREATE STATISTICS IF NOT EXISTS orders_customer_status (dependencies, ndistinct)
    ON customer_id, status FROM app.orders;
ANALYZE app.orders;

-- 4. autovacuum обратно
ALTER TABLE app.orders SET (autovacuum_enabled = true);
```

Для очень больших таблиц разумно ужесточить autovacuum:

```sql
ALTER TABLE app.orders SET (autovacuum_vacuum_scale_factor = 0.02,
                            autovacuum_analyze_scale_factor = 0.01);
```

## 10. Проверка целостности

```sql
CREATE EXTENSION IF NOT EXISTS amcheck;

SELECT bt_index_check('app.idx_orders_customer'::regclass, true);   -- heapallindexed
```

Для больших индексов `heapallindexed = true` дорог — выполняется выборочно для критичных
индексов; полный обход — `pg_amcheck --all` по регламенту окна.

Итоговая сверка объектов с инвентарём:

```sql
SELECT 'tables' AS kind, count(*) FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='app' AND c.relkind='r'
UNION ALL SELECT 'indexes', count(*) FROM pg_indexes WHERE schemaname='app'
UNION ALL SELECT 'views', count(*) FROM pg_views WHERE schemaname='app'
UNION ALL SELECT 'matviews', count(*) FROM pg_matviews WHERE schemaname='app'
UNION ALL SELECT 'functions', count(*) FROM pg_proc p JOIN pg_namespace n ON n.oid=p.pronamespace
WHERE n.nspname='app'
UNION ALL SELECT 'triggers', count(*) FROM pg_trigger t JOIN pg_class c ON c.oid=t.tgrelid
JOIN pg_namespace n ON n.oid=c.relnamespace WHERE n.nspname='app' AND NOT t.tgisinternal
UNION ALL SELECT 'fk', count(*) FROM pg_constraint k JOIN pg_namespace n ON n.oid=k.connamespace
WHERE n.nspname='app' AND k.contype='f'
UNION ALL SELECT 'check', count(*) FROM pg_constraint k JOIN pg_namespace n ON n.oid=k.connamespace
WHERE n.nspname='app' AND k.contype='c';
```

Числа сверяются с инвентарём построчно; каждое расхождение объясняется.

## Готово, когда

- [ ] все индексы валидны, недостающие созданы, `INCLUDE` и фильтры воспроизведены;
- [ ] все ФК созданы, `convalidated = true` у каждой;
- [ ] `CHECK` созданы и валидированы, нарушения либо исправлены, либо оформлены как исключение;
- [ ] уникальные ограничения с NULL сохранили семантику MSSQL (`NULLS NOT DISTINCT`);
- [ ] identity включены, `setval` выполнен, тестовая вставка проходит;
- [ ] `DEFAULT` восстановлены и совпадают с решением 13.4;
- [ ] триггеры, функции, представления и матвью созданы, состояние триггеров проверено;
- [ ] права выданы по реестру, приложение не может создавать объекты;
- [ ] `ANALYZE` выполнен, расширенная статистика создана там, где нужна;
- [ ] `amcheck` по критичным индексам пройден;
- [ ] количество объектов совпадает с инвентарём, расхождения объяснены;
- [ ] autovacuum включён, параметры загрузки сброшены.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| вставка падает на `duplicate key` после миграции | последовательность не выставлена | `setval` по `max(id)` |
| приложение вставляет явный `id` — отказ | `GENERATED ALWAYS` вместо `BY DEFAULT` | пересоздать как `BY DEFAULT` |
| `VALIDATE CONSTRAINT` идёт часами | большой объём, слабый I/O | валидировать в окне, по одной таблице |
| ФК не создаётся | нарушение в данных | найти сирот запросом раздела 3, исправить данные |
| триггеры сработали на загрузке | созданы до `COPY` | создавать после, либо `session_replication_role = replica` (нужен суперпользователь) |
| матвью не обновляется `CONCURRENTLY` | нет уникального индекса | создать `UNIQUE INDEX` на матвью |
| приложение не видит новые таблицы | гранты не выданы на объекты, созданные миграцией | `ALTER DEFAULT PRIVILEGES` + разовый `GRANT` |
| запросы после миграции идут медленно | нет статистики | `ANALYZE`, `SET STATISTICS`, расширенная статистика |
