# 13.8 Пошаговый прогон полной миграции

Инструкция к этапу 9 плана. Результат этапа: полный прогон в согласованном окне, ошибок нет,
rejected rows нет, длительность и ресурсы зафиксированы, после загрузки созданы индексы, ФК и
ограничения, ограничения валидированы.

Предусловия: пилот (этап 8) пройден, оценки уточнены, окно согласовано, загрузочный файл
проверен `--dry-run`, секреты разложены (13.6), целевая схема готова (13.5).

## 1. Pre-flight (за 30–60 минут до окна)

```bash
# 1. ресурсы приёмника
df -h /var/lib/postgresql /var/lib/pg_wal     # место на данные и WAL
free -g
nproc

# 2. параметры на время загрузки (13.5)
psql -d target_db -c "show maintenance_work_mem; show max_wal_size; show jit;"
psql -d target_db -c "select count(*) from pg_stat_activity where state <> 'idle';"

# 3. autovacuum выключен на загружаемых таблицах
psql -d target_db -c "select relname, reloptions from pg_class c join pg_namespace n on n.oid=c.relnamespace
                      where n.nspname='app' and c.relkind='r' and reloptions is not null;"

# 4. доступ к источнику и приёмнику
printf 'select 1\ngo\n' | tsql -S "$MSSQL_HOST" -p 1433 -U "$MSSQL_USER" -P "$MSSQL_PWD" -D "$MSSQL_DB"
psql -d target_db -c "select 1"

# 5. файловая система под --root-dir и логи
test -w /var/lib/pgloader && df -h /var/lib/pgloader

# 6. запись в источник прекращена (или дельта согласована)
```

Отдельно фиксируется **точка отсчёта**: время остановки записи и `last_lsn`/время снимка T-0
(13.3) — без них невозможно доказать, что сравнение корректное.

## 2. Запуск

Прогон запускается так, чтобы обрыв SSH его не убил:

```bash
tmux new -s migr      # или nohup ... &
cd /etc/pgloader

export MSSQL_USER=migr_ro MSSQL_HOST=... MSSQL_DB=source_db
export PG_USER=migr_etl PG_HOST=... PG_DB=target_db
export PGPASSFILE=/home/pgloader/.pgpass
export MSSQL_PWD="$(cat /run/secrets/mssql_migr_ro)"

time pgloader --logfile /var/log/pgloader/full-20261119.log \
              --root-dir /var/lib/pgloader \
              --summary /var/log/pgloader/full-20261119-summary.csv \
              ms.load
```

Порядок файлов, если загрузка разбита:

```bash
for f in 10-reference.load 20-small.load 30-medium.load 40-large.load 50-lob.load; do
  echo "=== $f $(date -Is)"
  pgloader --logfile "/var/log/pgloader/${f%.load}.log" \
           --summary "/var/log/pgloader/${f%.load}-summary.csv" "$f" || { echo "FAILED $f"; break; }
done
```

`|| break` — потому что продолжать после ошибки в справочной таблице бессмысленно: дальше поедут
нарушения ФК и мусорные ссылки.

## 3. Мониторинг во время прогона

**Прогресс COPY на стороне PostgreSQL** (PG 14+; набор колонок зависит от версии — сверить
`\d+ pg_stat_progress_copy`):

```sql
SELECT pid, datname, relid::regclass AS table_name, command,
       bytes_processed, tuples_processed,
       now() - query_start AS elapsed
FROM pg_stat_progress_copy
ORDER BY elapsed DESC;
```

**Активность и блокировки:**

```sql
SELECT pid, usename, state, wait_event_type, wait_event,
       now() - query_start AS elapsed, left(query, 80) AS query
FROM pg_stat_activity
WHERE datname = 'target_db'
ORDER BY elapsed DESC
LIMIT 20;
```

**WAL и чекпоинты** (рост WAL — риск заполнить том):

```sql
SELECT pg_size_pretty(sum(size)) AS wal_total FROM pg_ls_waldir();
SELECT * FROM pg_stat_wal;
```

**ОС:**

```bash
iostat -x 10 3          # утилизация диска приёмника
vmstat 5 6              # swap, CPU
iftop -i eth0           # сеть до источника
tail -f /var/log/pgloader/full-20261119.log
ls -l /var/lib/pgloader/          # reject.dat / reject.log
```

Что считать тревожным сигналом: `reject.dat` растёт; `wait_event = 'IO:DataFileWrite'` дольше
десятков секунд с падением пропускной способности; свободное место на приёмнике меньше 20%;
`swap` не нулевой на хосте pgloader.

## 4. Обработка ошибок по ходу

| Событие | Действие |
|---|---|
| единичные rejected rows | не останавливать прогон, сохранить `reject.dat`, разобрать после; на боевом прогоне — ноль |
| ошибка типа/длины | остановить, поправить `CAST` (13.4), перезапустить только затронутую таблицу |
| дубли ключей при построении индекса | данные нарушают уникальность: разобрать в 13.9 через `NOT VALID` или чистку |
| кончилось место | остановить, расширить том, перезапустить; WAL не удалять вручную |
| загрузка «встала» без ошибок | посмотреть `pg_stat_activity`: ждёт блокировку, чекпоинт или I/O |
| обрыв связи с источником | pgloader упадёт; перезапуск таблицы целиком (`truncate`) |

Остановка прогона: `Ctrl+C` в tmux (pgloader корректно закрывает батчи) либо `pg_terminate_backend`
для зависшего `COPY` — но тогда таблица останется частично загруженной и потребует `truncate` и
повторного прогона.

## 5. После загрузки (сразу, в том же окне)

```sql
-- 1. вернуть autovacuum и собрать статистику
ALTER TABLE app.orders SET (autovacuum_enabled = true);
VACUUM (ANALYZE) app.orders;

-- 2. проверить, что таблиц/строк столько же, сколько в снимке (быстрая проверка)
SELECT relname, n_live_tup FROM pg_stat_user_tables WHERE schemaname = 'app' ORDER BY 2 DESC;

-- 3. проверить, что индексы валидны
SELECT c.relname AS index_name, i.indisvalid, i.indisready
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'app' AND NOT i.indisvalid;

-- 4. статистика по загрузке
SELECT * FROM pg_stat_database WHERE datname = 'target_db';
```

Затем — 13.9 (последовательности, ФК, DEFAULT, CHECK, права, код) и 13.10 (валидация).

## Готово, когда

- [ ] pre-flight выполнен, точка отсчёта зафиксирована;
- [ ] прогон выполнен в окне, без обрывов сессии;
- [ ] rejected rows = 0 (или каждая строка разобрана и объяснена);
- [ ] `--summary` сохранён, число строк совпадает со снимком T-0;
- [ ] индексы созданы и валидны (`indisvalid = true`), невалидных нет;
- [ ] ФК, CHECK и DEFAULT созданы и валидированы (13.9);
- [ ] autovacuum возвращён, `VACUUM (ANALYZE)` выполнен;
- [ ] протокол раздела 6 заполнен, длительность и ресурсы записаны;
- [ ] свободное место и WAL вернулись в норму, повторный чекпоинт не идёт лавиной.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `canceling statement due to statement timeout` | серверный таймаут | `SET statement_timeout to '0'` в загрузочном файле |
| `invalid input syntax for type timestamp` | сентинелы `1900-01-01`, `9999-12-31` и подобные | правило `CAST` с `using`/`drop default`, разбор значений |
| `value too long for type character varying(n)` | `keep typemod` + многобайтовая кириллица | увеличить длину или оставить `text` для этих колонок |
| `duplicate key value violates unique constraint` | данные содержат дубли | `NOT VALID`/чистка данных, решение в 13.9 |
| `No space left on device` | WAL/данные/`--root-dir` | расширить том, уменьшить `max_wal_size`, повторить |
| прогресс стоит на одной таблице | блокировка или огромный LOB | `pg_stat_activity`, `pg_locks`; при необходимости вынести таблицу отдельно |
| после прогона приложение «не видит» таблицы | `search_path`/права | проверить `ALTER DEFAULT PRIVILEGES` и `search_path` приложения |
| повторный прогон падает на существующих объектах | нет `truncate`/`include no drop` согласованы | привести файл к режиму из 13.7 |
