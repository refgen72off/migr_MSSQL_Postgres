## 1. Назначение

1.1. Определить порядок работ по переносу одной базы данных MS SQL Server в Tantor 18 с помощью pgloader: от инвентаризации источника до приёмки и отката.

1.2. Зафиксировать границы возможностей pgloader, чтобы объём ручной работы (хранимый код, ограничения, привилегии, задания) был известен заранее, а не обнаружился в ночь переключения.

1.3. Обеспечить воспроизводимость: резервная копия, снимок исходного состояния и загрузочный файл хранятся как артефакты проекта, любой прогон повторяется с нуля.

**Что НЕ входит в этот документ:**

- миграция кластера целиком (несколько БД, Always On, реплики) — схема работ та же, но добавляется оркестрация по БД и общий простой;
- перенос серверной части 1С и её настроек — это отдельный сценарий;
- перевод приложений на новый драйвер/строку подключения — только как точка переключения (раздел 9).

## 3. Роли и ресурсы

- **DBA источника**: доступ на чтение каталога и данных, выгрузка DDL и резервной копии, блокировка изменений на время финального переноса.
- **DBA приёмника**: развёртывание Tantor, роли и права, настройка, приёмка, бэкап.
- **Разработчик/владелец приложения**: переписывание T-SQL, настройка соединений и драйверов, функциональные тесты.
- **Тестовый стенд**: копия источника (или его репрезентативная выборка) + экземпляр Tantor. Без стенда работы не начинаются: перенос «сразу в прод» недопустим.
- **Учётные записи**: отдельная учётная запись миграции на источнике (только чтение) и на приёмнике (только необходимое для загрузки), отдельный пользователь приложения; `sa` и `postgres` в работах не используются.

## 4. Что делает и чего не делает pgloader

### 4.1. Берёт на себя

- чтение каталога MS SQL и создание таблиц, первичных и уникальных ключей, внешних ключей, части индексов;
- последовательный потоковый перенос данных через `COPY` (быстро, без промежуточных дампов), с параллельными потоками и курсорами;
- преобразование типов по штатным правилам и по пользовательским `CAST`;
- перенос представлений «как данных» (`MATERIALIZE VIEWS`), фильтры по схемам/таблицам, переименование схем (`dbo` → `public`), частичное переименование таблиц.

### 4.2. Не берёт на себя (ручная работа, планируется отдельно)

- хранимые процедуры, функции, триггеры: переписывание на PL/pgSQL;
- `DEFAULT`-значения, `CHECK`-ограничения, computed-колонки — проверять и восстанавливать вручную;
- идентичность и последовательности: проверка и донастройка (`GENERATED AS IDENTITY` / `setval`);
- индексы с `INCLUDE`, фильтрованные индексы, кластерные/некластерные особенности, full-text и spatial-индексы;
- логины, пользователи, роли, привилегии, владение объектами;
- Agent jobs, linked servers, Service Broker, CLR, SSIS, расширенные свойства и `MS_Description`;
- инкрементальный перенос/CDC: pgloader делает полную загрузку, повторный запуск по таблице перезаливает её целиком (см. раздел 5.3);
- настройка целевого экземпляра (конфигурация, autovacuum, бэкап, мониторинг) — отдельная работа DBA приёмника.

### 4.3. Штатные соответствия типов

По документации pgloader; проверяются на пилоте и при необходимости переопределяются через `CAST`.

| MS SQL Server | PostgreSQL | Замечание |
|---|---|---|
| `tinyint` | `smallint` | |
| `float` / `real` | `float` / `real` | через `float-to-string` |
| `numeric` / `decimal` | `numeric` | через `float-to-string` |
| `money` / `smallmoney` | `numeric` | |
| `char` / `nchar` / `varchar` / `nvarchar` / `xml` | `text` | типовая длина отбрасывается |
| `binary` / `varbinary` | `bytea` | |
| `datetime` / `datetime2` | `timestamptz` | сдвиг часового пояса — проверить |
| `bit` | `boolean` | |
| `uniqueidentifier` | `uuid` | |
| `hierarchyid` / `geography` | `bytea` | структура теряется — решение принимать отдельно |

Отдельно проверяются `datetimeoffset`, `time`, `date`, `image`/`ntext`/`text`, `varbinary(max)`, `sql_variant`, `geometry`, `ROWVERSION`/`TIMESTAMP` — для них правил по умолчанию нет либо результат неудовлетворителен; нужны явные правила `CAST` или исключение колонки с ручной обработкой.

## 5. Стратегия переноса

**5.1. Вариант A — окно остановки записи.** Источник переводится в режим «только чтение» (остановка приложений или запрет записи), выполняется финальный прогон, валидация, затем переключение. Применяется, когда простой согласован и укладывается в оценку по пилоту. Это предпочтительный вариант: дельта не нужна, расхождений по определению нет.

**5.2. Вариант B — предварительный перенос + дельта.** Основной объём переносится на «холодном» снимке заранее, затем в окно останова применяется дельта изменений. Вариант выбирается, только если окно A неприемлемо: он добавляет отдельный механизм и отдельный класс ошибок.

**5.3. Механизмы дельты (вариант B).** Нативного переноса изменений «MSSQL → PostgreSQL» нет ни у pgloader, ни у PostgreSQL; логическая репликация PostgreSQL здесь не работает, потому что источник не PostgreSQL. Реалистичные варианты:

- `CDC` в MS SQL (`cdc.capture_instance`) + собственный аппликатор изменений (upsert по первичному ключу, порядок по LSN, повторный проход для догона);
- Debezium (SQL Server connector) с приёмником в PostgreSQL через sink-коннектор — отдельная инфраструктура (Kafka/Connect), оправдана при больших объёмах и повторяемых миграциях;
- «повторная синхронизация изменённых данных»: перезагрузка таблиц, затронутых за окно, по ключу/дате изменения; годится для баз с малым числом «горячих» таблиц.

Любой из вариантов требует, чтобы у таблиц был надёжный ключ (или дата изменения с гарантией монотонности) и чтобы дельта была проверена так же, как основной объём (раздел 8). Если таких гарантий нет — выбирается вариант A.

**5.4. Повторяемость.** Загрузочный файл pgloader, снимок исходного состояния и скрипты проверки хранятся в репозитории проекта; прогон на стенде воспроизводится одной командой. Это же даёт тренировку окна переключения.

**5.5. Осторожно с пересозданием.** pgloader пересоздаёт объекты в целевой схеме; конструкция `before load do $$ drop schema if exists ... cascade; $$` удаляет данные в приёмнике — на стенде с чужими данными это недопустимо.

## 7. Ключевые технические решения (принимаются до этапа 5)

**7.1. Кодировка и локаль целевой БД.**

- БД создаётся в `UTF8`; данные источника в однобайтовой кириллице (cp1251) переносятся с преобразованием — проверить выборочно до и после (кириллица, ё, спецсимволы, длинные строки).
- Провайдер локали (ICU / builtin / libc) и правила сортировки выбираются один раз и фиксируются в документе: смена после загрузки — это переиндексация.

**7.2. Регистр и имена.**

- MS SQL в случае нечувствительной collation не различает `'Иванов'` и `'иванов'`, а также регистр имён объектов; в PostgreSQL имена без кавычек приводятся к нижнему регистру, а сравнение строк регистрозависимо. Следствия: (а) возможны конфликты имён после приведения к нижнему регистру; (б) запросы приложения могут изменить результат. Решения: цитирование имён при переносе, `CITEXT`/функциональные индексы, явные `COLLATE`, правка запросов.
- Имена длиннее 63 байт усекаются — проверить на инвентаризации.
- Зарезервированные слова и объекты с пробелами/спецсимволами — список заранее.

**7.3. Идентичность и последовательности.** Для колонок-идентификаторов выбирается единый подход (`GENERATED BY DEFAULT AS IDENTITY` либо явная последовательность), после загрузки значения синхронизируются с `max(id)` — иначе первые же вставки дадут конфликт ключа.

**7.4. Схемы.** Схема `dbo` переименовывается в `public` (`ALTER SCHEMA 'dbo' RENAME TO 'public'`); прочие схемы переносятся как есть, права на схему выдаются отдельно.

**7.5. Порядок создания объектов.** Таблицы → данные → вторичные индексы → FK и `CHECK` → триггеры и код. Причины: загрузка в уже индексированную схему заметно медленнее (индекс перестраивается на каждой вставке, растёт фрагментация), а триггеры на время загрузки либо срабатывают лишний раз, либо требуют отключения; ошибки данных не маскируются под ошибки схемы.

**7.6. Ограничения и проверки.** `CHECK`-ограничения и `DEFAULT`-значения переносятся вручную после сверки семантики (в MS SQL и PostgreSQL различаются, например, поведение по умолчанию для пустых строк и дат).

**7.7. Роли и минимальные права.** Роль миграции получает ровно то, что нужно для загрузки: `CREATE`/`USAGE` на схему, вставку, создание индексов и ограничений; пользователь приложения — только права на свои объекты. Права `SUPERUSER`/`sa`/владелец кластера не выдаются. Права на источник: чтение каталога и данных, без записи.

**7.8. Секреты и сеть.** Пароли не попадают в командную строку, в историю shell, в загрузочный файл и в репозиторий: для целевой БД pgloader берёт пароль из `~/.pgpass` (или файла из `PGPASSFILE`), для источника — из переменной окружения сессии или защищённого файла доступа с правами `600`; в CI/Ansible — из хранилища секретов. Сетевые требования: TCP от хоста pgloader к `1433` источника и `5432` приёмника, открытые только для этого хоста, с проверкой `telnet`/`psql`/`--dry-run` до начала работ.

**7.9. Большие таблицы и LOB.** Крупные таблицы выносятся в отдельные загрузочные файлы с индивидуальными параметрами (число потоков, размер батча), чтобы падение одной таблицы не сбрасывало весь прогон.

## 8. Валидация и приёмка

Для каждого пункта — бинарный критерий; «похоже на правду» не считается. База сравнения — снимок из этапа 3.

**8.1. Структура.** Количество таблиц/колонок/ключей/индексов/sequence совпадает со снимком; список расхождений оформлен и объяснён; имена без неожиданного нижнего регистра.

**8.2. Данные.**

- счётчики строк по каждой таблице (источник: `COUNT_BIG(*)`; приёмник: `count(*)`), расхождение = 0;
- агрегаты по ключевым колонкам: `sum`/`min`/`max`/количество `NULL`, min/max дат (сверка с этапом 3);
- контрольные выборки по крупным и «денежным» таблицам; для критичных таблиц — полное сравнение упорядоченных выгрузок, поскольку прямого сравнения контрольных сумм между СУБД нет;
- LOB и текст: проверка отсутствия обрезания (максимальные длины, первые/последние записи), binary-данные — побайтовое сравнение выборки.

**8.3. Целостность.** FK валидированы (`VALIDATE CONSTRAINT`), уникальные индексы построены, непригодных индексов нет (проверка `indisvalid`), для btree доступен `pg_amcheck`; последовательности выставлены по `max(id)` и проверены тестовой вставкой.

**8.4. Функциональность.** Ключевые бизнес-отчёты и одинаковые запросы, выполненные в обеих СУБД, дают идентичный результат; расхождения объяснены (сортировка, регистр, округление, часовой пояс).

**8.5. Производительность.** Сравниваются планы и время 5–10 тяжёлых запросов; после загрузки обязательно собрать статистику (`vacuumdb --analyze-only`), иначе первые планы будут ошибочными; проверяется поведение приложения под типовой нагрузкой.

**8.6. Эксплуатация.** Бэкап приёмника проверен восстановлением, мониторинг видит новый экземпляр, алерты настроены.

## 9. Переключение приложения

9.1. Переключение — отдельный вид работ, а не «правка строки подключения». Проверяются: строка подключения и порт; драйвер (например `Microsoft.Data.SqlClient` → `Npgsql` / JDBC PostgreSQL); диалект SQL и параметры команд (имена параметров, `TOP` → `LIMIT`, `ISNULL` → `COALESCE`, `+` для строк, работа с датами); параметры пула соединений и таймауты; транзакционная логика (уровни изоляции, `READ COMMITTED` в MSSQL и PostgreSQL ведут себя по-разному); обработка ошибок и кодов возврата.

9.2. Переключение выполняется в согласованном окне после этапа 9 и валидации этапа 10, при готовом коде этапа 12 (см. зависимость в разделе 6).

9.3. MSSQL остаётся доступным для сверки и отката до завершения приёмочных тестов и подписания приёмки; запись в него после переключения запрещается (иначе сверка и откат теряют смысл).

9.4. Точка невозврата фиксируется явно: до неё откат — возврат строки подключения, после — восстановление из копии приёмника и разбор расхождений.

## 10. Откат

10.1. Источник на всё время работ остаётся в рабочем состоянии и не изменяется: откат до точки невозврата = возврат приложений к прежней строке подключения.

10.2. Условия отката фиксируются заранее: превышение окна простоя, расхождение данных, непройденные функциональные тесты.

10.3. Решение об откате принимает ответственный, назначенный на этапе 1; решение оформляется одной записью с временем и причиной.

10.4. После переключения источник не удаляется минимум до завершения наблюдения и подписания приёмки.

## 11. Риски и меры

| Риск | Мера |
|---|---|
| Резервная копия снята, но не проверена — восстанавливать нечем | тестовое восстановление на отдельном экземпляре в рамках этапа 2, до любых работ |
| Код и объекты, которые pgloader не переносит (процедуры, триггеры, задания), оказываются недооценены | инвентаризация на этапе 1 с перечнем объектов и ответственным за каждый; параллельная ветка этапа 12 |
| Загрузка в уже индексированную схему: медленно и с фрагментацией индексов | порядок 7.5, загрузка в «голые» таблицы (этап 6) |
| Тихие искажения при преобразовании типов (`datetime` → `timestamptz` со сдвигом часового пояса, потеря структуры `geography`/`hierarchyid`, отбрасывание длины у `varchar`, деньги через `numeric` с иной точностью) | пилот на реальных данных, явные `CAST`-правила, сверка агрегатов |
| Регистрозависимость PostgreSQL меняет результаты запросов, которые в MS SQL работали «по-другому» | раздел 7.2 и отдельный тест с поиском по кириллице в разных регистрах |
| Скорость pgloader на реальном объёме ниже оценки (сеть, LOB, параллелизм) | замер на пилоте, потоки/батчи подбираются по факту, при необходимости — перенос больших таблиц отдельными прогонами |
| Неприемлемо длинный простой | вариант A с тренировкой окна на стенде либо вариант B с дельтой (5.2–5.3) |
| Дельта теряет изменения или применяется не по порядку | только при надёжном ключе/монотонной дате, аппликатор с идемпотентным upsert, сверка дельты как основного объёма, иначе — вариант A |
| Пароли и строки подключения утекают в историю shell, логи или репозиторий | раздел 7.8: `.pgpass`/`PGPASSFILE`, переменные окружения, secrets, права `600`, проверка логов pgloader на отсутствие паролей |
| Версия и сборка pgloader различаются между стендом и продом (в 3.6.x подключение к MSSQL идёт через FreeTDS, в готовящейся ветке 4.x — через JDBC-драйвер Microsoft) | зафиксировать версию и способ установки, прогонять на том же дистрибутиве, что и прод |
| Переключение приложения раньше готовности кода или прав | явная проверка готовности этапа 12 перед этапом 11 |
| Стенд с реальными данными вне регламента (персональные данные) | обезличивание или тестовая выборка, согласование заранее |

## 12. Открытые вопросы

12.1. Источник — одна конкретная БД или типовой сценарий для нескольких заказчиков? От этого зависит, нужен ли шаблон загрузочного файла.

12.2. Есть ли в базе хранимый код, и кто его переписывает (разработчик заказчика или наша сторона)?

12.3. Можно ли останавливать запись; если нет — какой механизм дельты приемлем (CDC + аппликатор, Debezium, повторная синхронизация)?

12.4. Какое окно простоя допустимо и кто его согласует; кто объявляет точку невозврата?

12.5. Нужен ли перенос прав доступа «как есть» или достаточно ролей по регламенту Tantor?

12.6. Используется ли 1С; если да — синхронизировать с документом по миграции 1С (там свои требования к локали и настройкам).

## 13. Состав следующего документа (подробная инструкция)

13.1. **Инвентаризация**: готовые T-SQL-запросы (объекты по типам, объёмы, индексы, FK, дефолты, identity, collation, jobs, linked servers) и форма таблицы инвентаря.

13.2. **Резервное копирование и проверка восстановления**: команды `BACKUP DATABASE ... WITH CHECKSUM`, `RESTORE VERIFYONLY`, восстановление на отдельный экземпляр, выгрузка DDL (`SMO`/скрипты) и прав.

13.3. **Снимок состояния**: скрипты снятия счётчиков и агрегатов, формат хранения, повторный съём для сверки.

13.4. **Проверка совместимости**: разбор типов без эквивалента, правила `CAST`, список переименований, разбор computed columns и `DEFAULT`, отчёт о ручных работах.

13.5. **Подготовка приёмника**: установка Tantor 18, создание БД и схем, роль миграции и пользователь приложения с минимальными правами (`CREATE ROLE`, `GRANT`), настройка `pg_hba.conf`, бэкап и мониторинг.

13.6. **Установка и настройка pgloader**: выбор версии, сборка/пакет, FreeTDS (`tds version 7.4`, `client charset UTF-8`) либо JDBC, `.pgpass`/`PGPASSFILE`, проверка подключения, `--dry-run`.

13.7. **Загрузочный файл**: полный разбор всех использованных клауз, отдельные файлы для крупных таблиц, порядок «данные → индексы → ограничения», фильтры и `ALTER SCHEMA`.

13.8. **Пошаговый прогон**: команды, ожидаемый вывод, типовые ошибки и их лечение (кодировка, таймаут, права, несовместимые типы, дубли ключей, rejected rows), контроль диска/памяти/сети.

13.9. **Пост-обработка**: последовательности и `setval`, FK и `CHECK`, триггеры и код, привилегии, статистика, пересборка индексов, представления.

13.10. **Валидация**: готовые SQL-запросы сверки по каждой таблице, чек-лист приёмки, шаблон протокола расхождений.

13.11. **Дельта (если выбран вариант B)**: настройка CDC на источнике, аппликатор изменений, порядок применения, проверка.

13.12. **Переключение и откат**: точная последовательность команд с временными метками, чек-лист приложения (драйверы, пулы, диалект, транзакции), шаблон записи о решении и о точке невозврата.

13.13. **Приложения**: таблица «конструкция T-SQL → замена в PostgreSQL» по объектам реальной базы (по итогам этапов 4 и 12).
